# 구조화 정책·검증·첫 온보딩 구현 — 2026-09-24

사용자 요청에 따른 개인 테스트 앱 업데이트. 정책 설정 변경 범위를 실제 코드로 연결한다. Phase 0 전체 및 광범위한 신뢰성 게이트는 여전히 별도다.

## 구현

- OpenAI가 strict schema로 범위·조건·동작·예외·시간·enabled와 변경 목록을 생성한다. 기존 Jev compile 호출은 차단됐으며 Jev는 새 알림 일치 판단에만 사용한다.
- 앱이 허용 값·필드·실제 대상·ID·조건 조합·시간 범위·operation/Diff 일치·같은 조건의 충돌을 검사한다. 삭제·숨김·범위/시간 변경·예외·다중 변경·모호함은 독립 OpenAI 의미 검증을 거친다. valid/invalid/clarification_required와 질문·실제 대화 선택을 연결했다.
- 검증된 제안은 base revision과 해시로 확인에 연결한다. 수정안과 실제 저장 내용이 달라지거나 현재 버전이 바뀌면 적용하지 않는다. 이전 활성 정책을 유지하고 제안·입력은 보관한다.
- 기준 화면은 적용 범위별 그룹, 조건 → 동작, 하위 예외, 체크·삭제·Action/Scope 직접 변경, AI 수정, 변경 중심 Diff와 유지 항목 펼치기를 제공한다.
- 정책 상태·제안·온보딩·버전은 별도 Room DB `policies.db`에 원자적으로 저장한다. 기존 AtomicFile은 최초 읽기 때 보존 이관한다. 알림 DB/원문은 변경하지 않는다.
- 기존 자연어 실행 정책은 의미를 임의 변환하지 않고 계속 유지한다. ‘기존 기준 정리·확인’을 눌러 OpenAI가 변환안을 만들고 사용자가 확인하면 새 실행 모델로 바뀐다. 이전 형식이 남은 상태에서 일반 AI 수정 요청을 해도 기존 지시를 함께 전달하고 의미 검증을 의무 실행하며, 확인 화면에 이전 지시를 표시한다. 이전 정책 스냅샷을 보존한다. 이전 미완성 입력도 새 정책으로 이어서 정리할 수 있다.
- 첫 사용자는 권한 → 앱별 처리 → 꼭 볼 내용 → 관심/줄일 내용 → 예시/최종 확인의 5단계를 사용한다. 기존 사용자는 설정의 ‘처음 설정 안내 다시 보기’로 진입한다. 관찰된 앱과 실제 대화만 제시하며 OS 알림 끄기는 설정 이동으로 구분한다.
- 시간은 고정 IANA 시간대, 요일, 자정 통과 구간, from/until로 저장한다. 시작 포함/종료 제외, 야간 구간은 시작 요일 기준이다. 알림 postedTime에 대해 판단하며 오래된 수신은 기존 원본 확인 처리다. 기기 시간대 변경으로 저장한 고정 시간대를 자동 변경하지 않는다. 임시 기간 종료는 해당 정책만 실행 대상에서 제외한다.
- Jev에는 앱 코드가 조건 타입을 명확한 의미 질문으로 변환해 전달한다. 모델은 개별 조건/근거 충분성만 판단하고 앱이 ANY/ALL/NOT의 3값 논리, 예외·범위 구체성·동작을 결정한다. 기본 SHOW이며 불확실성/충돌은 review로 표시한다. 일반 알림에 OpenAI를 호출하지 않는다.

## 현재 제한

- AI Watch 문맥 누적은 여전히 준비 중이며 WATCH 활성 정책은 거부한다. 작업 완료/입력 필요의 일반 알림 조건은 지원한다. 외부 앱/OS 알림 취소나 별도 푸시는 없다. QUIET는 Inbox에 남는다.
- 관계 범위는 실제 선택 대화 연결이 필요하다. 참여자 명단이나 과거 대화는 읽지 않는다. 발신자는 실제 관찰된 이름 기반이며 계정 식별 정보가 없는 동일 이름의 인물을 보편적으로 구분하지 못한다.
- 원문의 enum 예시를 실행 계약으로 통합했다. 추가 사용자 관심은 CONTENT 값으로 표현한다. 정책의 알 수 없는 enum은 거부하며 런타임 불확실성과 구분한다. 의미 validator의 질문 없음은 빈 문자열을 사용한다.
- 최대 30개 규칙, 규칙당 12개 조건·8개 예외, 전송/출력 한도가 있다. runtime 질문이 100개를 넘으면 원본 확인으로 남긴다. 임계값은 개발용 보수적 값이며 전 앱/언어에 대한 보정 완료를 뜻하지 않는다.
- 초기 모델/네트워크/응답 오류에는 자동 무제한 재시도하지 않는다. 현재 기준과 요청을 보존하고 다시 정리 경로를 제공한다. 모든 모호한 의미를 코드만으로 증명할 수 없어 위험 의미 검증과 사용자 확인을 함께 쓴다.

- 단위 테스트 53개 통과: 수집 11, 기존 선별 10, 독립 설정 7, 초안 2, 정책 검증/저장/이관 19, 구조화 런타임 4.
- debug/release APK 빌드 및 lint 통과. release에서 개인 테스트 키 파일과 debug 키 바이트가 발견되지 않았다.
- Galaxy S23 / Android 16에 debug APK 재설치. 최종 전체 실행은 5개 중 4개 통과, 1개는 정책 요청 중 연결/저장 오류로 중단됐다. 실패한 1개를 동일 입력·모델로 단독 재실행해 통과했다. 5개 시나리오 모두 통과 증거가 있지만 단일 실행 5/5라고 기록하지 않는다. 정확한 예외 정보가 남지 않아 해당 1회의 원인을 API 서버나 네트워크로 단정하지 않는다.
- 온보딩 단독 실기기 검사에서 단계 이동, 입력 저장, Activity 재생성 복원, 실제 OpenAI 정리, 최종 확인 클릭, 정책 저장 및 완료 플래그를 확인했다.
- 기존 사용자의 활성 정책은 변경하지 않았다. 합성 입력은 별도 Room DB/파일 경로로 격리했다.

### 실패에서 수정한 부분과 검증 한계

초기 실제 API 검사에서는 광고 숨김과 예외가 review로 남았다. enum/복합 그룹 질문을 개별 의미 질문으로 바꾸고 ANY/ALL/NOT 결합을 앱 코드로 옮겼다. 확정 true는 0.9 이상, false는 0.05 이하, 근거는 0.9 이상으로 유지했으며 통과를 위해 임계값을 낮추지 않았다.

‘기타 장비’는 악기와 그 밖의 장비로 해석될 수 있었다. 해당 모호한 입력의 실패 기록은 남기고, 최종 분류 검사는 ‘악기인 일렉기타와 기타 앰프’라고 명확히 지정한 별도 사례로 실행했다. 편집 프롬프트에는 다의어 재질문 원칙을 추가했다. 이것이 모든 모호한 요청의 정확도나 기존 대규모 평가의 통과를 뜻하지 않는다.

온보딩 검사에서 접근성 입력 뒤 Back이 이전 단계로 이동한 것을 복원 실패로 오인한 부분을 바로잡았다. 최종 확인 클릭은 스크롤 직후 전달되지 않아 저장 처리에 도달하지 않았다. 스크롤 정지 후 버튼을 다시 찾아 클릭했을 때 적용과 완료 저장이 통과했다. 앱의 저장 검증을 우회하지 않았다. 화면에는 기존 FLAG_SECURE가 적용돼 스크린샷으로 외관 검증을 하지 못했으며 접근성 컨트롤과 저장 상태를 검사했다.

최초 빌드의 Android JSON API 호출 오류를 수정했고, 빌드 산출물에 중복 생성된 `2.dex`/`3.dex`는 clean 빌드로 제거했다. 테스트용 기존 Jev compile/구형 UI 검사는 새 역할 계약에 맞게 교체했다. 예전 실기기 테스트 전체를 새 구현에서 다시 통과했다고 주장하지 않는다.

실제 수신 앱 전체, 한국어/영어 장기 정확도, 네트워크 중단·기기 재부팅·시간대 변경 실기기 행렬, 온보딩 소요 시간은 미검증이다. Phase 0 전체 및 광범위한 신뢰성 게이트는 유지한다.
