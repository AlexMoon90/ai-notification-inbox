# 정책 파이프라인 원인 분석 — 2026-09-25

## 확인된 원인

문제를 OpenAI의 JSON 생성 오류 하나로 설명할 수 없다. 실제 사례에서 다른 단계의 결함이 같은 ‘숨김이 안 됨’으로 나타났다.

| 단계 | 증거 / 결함 | 영향 |
|---|---|---|
| 정책 작성 | 과거 임의 ID, 기존 예외 보존 문제. strict schema는 문법만 보장하며 사용자 의미까지 증명하지 않음 | 저장 거부 또는 잘못된 제안 가능 |
| 정책→판정 질문 | 조건별 match와 evidence가 다른 대상을 질문. CONTENT/PROMOTION만 개별 보정, 나머지는 일반적인 본문 완전성 질문. evidence에 한정어 누락 | 올바른 JSON이어도 확정 판정 불가 |
| 판정 입력 | title을 conversationTitle로 대체. 최신 메시지의 동일 timestamp 순서와 null 처리, preview/긴 본문 검사에서 서로 다른 선택 | 같은 알림을 각 단계가 다르게 해석 |
| 결과 조합 | 후보 하나가 불확실하면 전체 보류. 이후 동일 동작 전용 예외 처리 추가 | 다른 조건의 불확실성이 확정된 결과를 취소 |
| 수신 처리 | 앱 자체 일일 200건 제한, 같은 알림 갱신의 중복 판정 | 모델에 보내기도 전에 중단. 이전 작업에서 제한 제거·중복 캐시 적용 |
| 관측/평가 | 개별 고정 JSON 및 모의 결과 검사 위주. 과거 대규모 Python 평가와 현재 Android 실행 경로가 다름 | 부분 통과를 실제 전체 경로 신뢰도로 오인할 위험 |
| 과거 결과 | 기존 정책 버전의 판정을 새 버전으로 자동 재계산하지 않음 | 새 수신 개선과 기존 화면의 과거 오류가 혼재 |

구체적 기록: `evaluations/promotion-evidence`, `evaluations/kakao-short-reply`, `evaluations/google-sports-hide`, `evaluations/no-daily-classification-cap`. 광고 사례는 match=.99/evidence=.63, 스포츠 사례는 match=.98/evidence=.79였다. 이는 JSON 오류의 증거가 아니라 실행 질문/판정 경계 문제의 증거다.

## 공통 수정

1. `conditionPredicate` 하나를 OpenAI 조건 카탈로그와 Jev 조건 판정에 사용한다. 모든 의미 조건에서 title+현재 text를 함께 사용하고 한정어를 보존한다. 부정은 코드에서 한 번만 적용한다. 새 앱·새 CONTENT 주제별 분기를 추가하지 않는다.
2. 최초 공통 evidence 개선안도 실제 API에서 실패했다. 17개 합성 알림 중 숨겨야 할 4개가 review였다. 세금 영수증/점심/의자 광고 등은 match=.01인데 evidence=.29~.62여서 ‘비해당’이 ‘정보 부족’으로 바뀌었다. `first-run.json`에 실패를 보존했다. 따라서 두 Noul 질문을 단순 재문구화하는 대신 조건마다 Jev Choice의 MATCH / NO_MATCH / UNKNOWN을 직접 받도록 바꿨다. 앱은 MATCH 확률≥.9, NO_MATCH 확률≥.95만 확정하고 UNKNOWN/그 외는 보류한다. 모델이 알림 행동을 선택하는 구조는 아니다. 기존 Noul 임계값과 숫자는 대응하지만 다른 분포이므로 의미 정확도/교정이 동등하다고 가정하지 않는다. 반환 타입·전체 선택지·확률 범위/합계·선택 최대값도 검증한다.
3. 미확정 판단이 true/false 어느 쪽이어도 최종 동작이 같을 때만 실행한다. 가능한 동작을 우선순위별로 계산한다. 결과를 바꿀 수 있는 SHOW 예외/충돌은 표시 보류한다. 하위의 사용되지 않는 분기가 상위 확정 동작을 취소하지 않는다.
4. 최신 메시지 선택을 공용화한다. 동일 timestamp는 배열 마지막, JSON null은 문자열 "null"로 취급하지 않는다. 빈 첨부 캡션을 과거 긴 본문으로 대체하지 않는다. 제목과 대화명을 별도 전달한다. 본문이 없어도 실제 제목이 있으면 의미 판정에 전달한다. 묶음 요약·알려진 잘림/과대 입력·지연 수신 가드는 유지한다.
5. ANY/EMPTY_CONTENT의 한정어는 저장 단계에서 거부한다. 이전에 저장된 잘못된 ANY도 실행 시 전체 숨김으로 확대하지 않는다.
6. 정책 검증 실패를 네트워크 실패와 구분하고 단계/오류 타입을 남긴다. 결정론적 검사에서 거부된 JSON도 원래 요청과 구체적 오류를 전달하여 최대 한 번 보완한다. 보완 후에는 결정론적 검사와 의미 검증을 모두 다시 통과해야 하며 자동 저장하지 않는다. 반복 실패는 기존 기준을 그대로 유지한다. 신규 시간 무제약 규칙에는 앱이 유효한 default_time을 제공한다. 진단 콜백의 제안 원문 수집은 합성 instrumentation에서만 사용하며 production 원문 로그를 추가하지 않는다.
7. 실행 결과에 원문 없는 정책 ID·우선순위·일치/미확정·가능 동작·계약 버전을 내부 기록한다. 사용자 화면에 기술 설명을 추가하지 않는다.

## 검증 원칙

- 고정 Boolean 판단을 넣는 코드 검증과 실제 API의 의미 검증을 별도로 보고한다.
- 규칙 3개 × true/false/unknown × SHOW/HIDE/QUIET × 우선순위: 5,832조합. 부모/예외 2개/경쟁 규칙: 2,187조합. 독립적인 모든 Boolean 대입 정답과 비교한다. 이는 코드 조합 정확성의 증거이며 AI 의미 정확도 8,019건을 뜻하지 않는다.
- 실제 Android PolicyController → strict JSON → deterministic/semantic 검증 → 격리 저장 → 새 manager로 재로드 → NotificationSelection → Jev → 최종 결과를 검사한다.
- 기대 동작은 사람이 미리 지정한다. OpenAI가 정답이나 합격 여부를 생성하지 않는다. 한국어/영어, 다른 앱 범위, 예외, ‘이것만’, 납부 완료 vs 납부 요구, 작업 완료 vs 승인 요구, 미관측 회사방을 포함한다.
- 생성 JSON도 결과 파일에 남겨 사람이 의미/범위/예외를 검토한다. 테스트 합성 알림만 저장하며 실제 사용자 정책/본문은 복사하지 않는다.

## 제품 신뢰도 게이트와 남은 한계

한 번의 소규모 합격으로 임의의 자연어 정확도를 보장할 수 없다. 출시 게이트는 아직 충족하지 않았다. 반복 실행, 학습/수정에 사용하지 않은 별도 조건, 다회차 추가/수정/삭제, 시간/대화/발신자 조합, 실제 앱 수신 형식, 서비스 장애를 확장해야 한다. false suppression, 숨김 누락, 불필요한 clarification/review를 각각 집계한다. 애매한 것은 보류한 경우와 명확히 정답을 낸 경우를 혼합하지 않는다.

실패 시 고정 fixture를 먼저 추가하고 입력→생성 정책→조건 판단→동작 조합→수신 가드 중 실패 단계를 지정한다. 전체 회귀를 통과한 공통 수정만 반영한다. 특정 팀/앱/문구용 예외 코드를 누적하는 것을 기본 해결책으로 삼지 않는다.

기존 결과의 재판정은 별도 범위다. 사용자 데이터/과거 결과를 이번 테스트에서 변경하지 않는다. Android 원래 앱 알림을 취소하지 않는다. 현재 Phase 전체 완료로 기록하지 않는다.

근거: [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs), [TypeSafe Noul](https://docs.typesafe.ai/primitives/noul), [TypeSafe Choice](https://docs.typesafe.ai/primitives/choice). 타입/스키마 준수와 의미 정확성은 별개다.

## 검사 중 추가로 드러난 한계

Choice 첫 검사에서 세금/광고/AI 작업 11개 알림은 기대한 숨김 여부를 충족했고 모호한 첨부 요청은 review였다. 그러나 Google/YouTube 두 요청이 편집 API 성공 뒤 제안 완료 전에 일반적인 연결/저장 오류로 종료됐다. 당시 상세 제안/예외 타입을 저장하지 않아 정확한 실패 필드를 소급 확정할 수 없다. 시간대 빈 문자열 등 검증 실패를 원인으로 단정하지 않는다. 실패 단계와 합성 제안 진단을 추가하고 결정론적 검증 오류 보완 경계를 강화했다. 이 실패도 전체 통과로 계산하지 않는다.

- 전체 경로 합성 알림 19개: HIDE 8, 명확한 표시 9, review 2. 숨김 여부 19/19 기대 충족. review 중 1개는 의도한 첨부/지시어 불완전 사례이고, 1개는 명확한 AI 승인 요청으로 불필요한 보류가 남았다. ‘모든 판정이 명확히 맞았다’로 계산하면 18/19이며 100%가 아니다.
