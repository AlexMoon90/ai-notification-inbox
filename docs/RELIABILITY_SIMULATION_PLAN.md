# 영미권 앱 기반 신뢰성 시뮬레이션 제안

작성·통계 확인: 2026-09-23. 사용자 요청에 따라 검증을 개발의 중심 작업으로 제안한다. 본 문서는 계획이며 아래 규모의 데이터 생성/API 실행/성능 달성을 의미하지 않는다. 현재 앱은 Phase 0 미완료다. 기존 독립 LLM 실험과 Jev 실험을 연결하는 검증이 먼저 필요하다.

## 1. 검증 목표

사용자 지시 → 부족한 정보 질문 → 답변 → 최종 텍스트 지시 → Jev 정책 JSON → Jev 알림 분류 → 앱 행동까지 의미가 보존되는지 확인한다. 실행용 정책 JSON은 Jev가 생성하고 OpenAI LLM은 실시간 반복 분류에 사용하지 않는다.

단순 JSON 문법 성공이나 그럴듯한 요약을 성공으로 세지 않는다. 사용자에게 알려야 할 알림이 실제 알림 대상으로 도달해야 한다. 기록만 남겨 놓고 적극 알림을 하지 않은 경우를 적극 알림 성공으로 세지 않는다. 사용자가 자신의 누락을 찾아주기를 기다리지 않는다.

기존 17/20 LLM 결과는 상태·질문 종류·일부 핵심값 검사다. 기존 Jev 128회 실험도 자연어 정책을 직접 입력한 별도 분류 실험으로, 정책 JSON 컴파일과 전체 경로 검증은 아직 아니다. [LLM 결과](LLM_POLICY_SETUP_SPIKE.md), [Jev 결과](JEV_REQUIREMENTS_EVALUATION.md).

## 2. 대상 시장과 이용 통계

첫 시장은 미국(en-US)·영국(en-GB) 성인 Android 사용자로 한정해 비교한다. 캐나다·호주까지 대표한다고 주장하지 않는다. 사용자 확인에 따라 한국어도 신규 필수 평가 언어에 포함하며, 한영 혼용도 별도 집계한다. 영어권 상황과 한국어 원문 사례를 각각 작성하고 단순 번역만으로 언어 검증을 대체하지 않는다.

Ofcom Online Nation 2025의 Ipsos iris 자료(Figure 16, PDF p.27)는 Android 앱 이용 도달률을 제공한다. WhatsApp 90%, Google Maps 83%, YouTube 80%, Gmail 76%, Facebook 74%, Google Messages 72%, Messenger 64%, Amazon 58%다. 본문·출처는 2025년 5월인데 그림 제목은 May 2024로 표기돼 있어 연도 불일치를 기록한다. 표기 문제 때문에 정밀 시장 점유율 가중치가 아닌 대상 선정 근거로 사용한다. [Ofcom 원문](https://www.ofcom.org.uk/siteassets/resources/documents/research-and-data/online-research/online-nation/2025/online-nations-report-2025.pdf)

### 자료 사용 원칙

- 최근 다운로드 순위를 지속적인 이용률로 취급하지 않는다. 미국·영국, Android·iOS, 일간·월간, 앱·웹 지표를 합쳐 하나의 인구 대표 순위로 만들지 않는다.
- 인기도는 테스트할 앱 선정 근거다. 앱별 알림 발생량·본문 형식·중요 알림 비율은 별도 자료가 필요하다.
- 본 평가 설계안: 70%는 위 통계로 선정한 앱 중심, 20%는 납부·보안·예약 등 손실 위험 보강, 10%는 드문 조건·미지원·공격적 입력 보강. 이 비율은 실제 시장 통계가 아니라 테스트 자원 배분이다. 세 집단 점수는 따로 보고한다.
- 미국/영국을 절반씩 배정하는 것도 시장 규모 추정이 아니라 국가별 비교 설계다. 인기도 기반 결과와 영역별 균형 결과를 모두 보고한다.
- ESPN 등 스포츠 앱, 은행/공공기관별 앱, 지역 서비스는 별도 시나리오 필요성으로 포함한다. 이번 자료로 특정 앱이 전체 이용 상위라고 주장하지 않는다.

## 3. 앱과 알림 내용을 함께 다양화

아래 문구/사건은 합성 설계 예시이며 실제 앱 알림 캡처나 실제 경기·납부 사실이 아니다. 하나의 사건이 Gmail·SMS·앱 푸시로 올 수 있으므로 주제와 전달 앱을 별도 축으로 둔다.

| 영역 | 우선 전달 앱 또는 보강 대상 | 요청 예시 | 반드시 구분할 사건 |
|---|---|---|---|
| 개인·가족 대화 | WhatsApp, Messenger, Google Messages | Only notify me when Alex needs a reply. | 직접 회신 요청 / 단순 이름 언급 / 다른 사람에게 요청 |
| 업무 대화 | Teams, Slack | Flag approvals assigned to me. | 내 승인 요청 / 동료 담당 / 완료 보고 |
| 이메일 | Gmail, Outlook | Tell me when a client needs a response. | 직접 요청 / 참조 공유 / 잘린 본문 |
| 스포츠 | 스포츠 앱 보강, Google·브라우저 알림 | Tell me the final score for my team. | 팀 미지정 / 경기 중 / 종료 / 정정 / 다른 팀 |
| 영상·채널 | YouTube | New uploads from this channel, not recommendations. | 업로드 / 라이브 / 추천 / 댓글 / 채널 정보 없음 |
| 소셜·커뮤니티 | Instagram, Facebook, Reddit, TikTok | Replies to my posts, not suggested posts. | 실제 답글 / 추천 / 광고 / 대상 미상 |
| 납부·금융 | Gmail, Messages, 금융 앱 보강 | Alert me if I need to make a payment. | 납부 예정 / 실패·미납 / 완료 / 상품 광고 |
| 쇼핑·배송 | Amazon, Walmart, eBay, Temu, SHEIN | Tell me if delivery needs action. | 주소 확인 / 수령 실패 / 단순 배송 현황 / 할인 |
| 일정·여행 | Google Calendar, Outlook, Maps, 여행 앱 보강 | Tell me if my booking changes. | 변경 / 제안 / 옛 일정 인용 / 예약 연결 불가 |
| 채용 | LinkedIn, Indeed, Gmail | Interview invitations, not job suggestions. | 면접 요청 / 추천 / 지원 완료 / 기한 변경 |
| 보안·계정 | Gmail, Messages, 앱 계정 알림 | New sign-ins to my account. | 실제 경고 / 기능 홍보 / 교육용 예문 / 계정 미상 |
| 학교·건강·지역 | 메일·메신저·지역 앱 보강 | Changes that affect my household. | 지정 대상 공지 / 타 지역 / 첨부만 있음 / 대상 미지정 |

미국/영국 별칭·구어체, football의 종목 차이, 날짜 순서(03/04), 시간대/DST, 달러/파운드, 이름 중복, 발신자와 언급 인물 차이도 포함한다. 날짜·스포츠 결과는 고정된 합성 시각과 사실을 사용하고 모델의 최신 지식에 의존하지 않는다. 이 목록은 시험 영역이며 기존 이벤트 카드 종류를 임의로 늘리는 제품 구현이 아니다. 스포츠/영상처럼 기존 분류명에 없는 선호도 의미 판단 자체가 가능한지 별도로 검사한다.

알림 유형 근거: YouTube는 업로드·라이브·추천 등 알림 설정이 있으며, Gmail은 계정/알림 설정으로 들어오는 알림 범위가 달라질 수 있다. ESPN은 점수·뉴스·경기 업데이트 알림을 안내한다. 공식 도움말은 유형의 근거일 뿐 Android title/extras 형식의 검증 자료가 아니다. [YouTube](https://support.google.com/youtube/answer/3382248?co=GENIE.Platform%3DAndroid&hl=en), [Gmail](https://support.google.com/mail/answer/1075549?co=GENIE.Platform%3DAndroid&hl=en), [ESPN](https://support.espn.com/hc/en-us/articles/115003858572-ESPN-Fantasy-App-and-Alerts).

## 4. 합성 사례에 숨은 정답을 넣지 않는 방법

각 사례는 아래 두 자료를 분리해 보관한다.

- 평가자용: 실제 사용자 의도, 질문받으면 답할 사실, 미정인 선호, 허용되는 질문/분기, 금지되는 임의 추가, 최종 조건, 모의 알림별 기대 행동과 근거.
- 제품 입력용: 최초 지시, 그때까지의 실제 답변, 관찰 가능한 후보/알림 필드, 앱 기능 안내, 현재 정책 버전과 현재까지의 문맥만 제공.

숨은 의도나 미래 알림, expected action은 제품 LLM/Jev에 전달하지 않는다. 사용자가 스스로 선호를 모르면 시뮬레이터도 임의로 정답을 말하지 않는다. 허용된 선택 분기에 따라 이후 기대 조건을 고정된 규칙으로 갱신한다.

알림마다 앱, 계정/프로필 범위, 시각, title/text, 방/발신자/채널 식별 가능 여부, 누락 필드, 요약·중복·업데이트 여부, 시점까지의 문맥을 기록한다. 전체 이메일·유튜브 구독 목록·방 참여자 명단을 알림에서 확보했다고 가정하지 않는다.

관찰되지 않은 세금 고지 자체를 AI가 알아야 한다고 채점하면 안 된다. 다음을 분리한다: 원본 앱 알림 미발생 / 리스너 미수집 / 정보는 도착했지만 판단 실패 / 판단은 맞지만 표시 실패. 수집 전 누락은 별도 기기 검증 대상이다.

## 5. 다중 에이전트 사용

대량 실행 시 다음 역할을 분리한다. 동시 에이전트 수보다 서로 보지 않는 정보와 검토 절차가 중요하다.

1. 사례 작성 담당: 통계로 선정된 앱·12개 영역의 합성 사용자/알림/반례 작성.
2. 정답 검토 담당: 작성자의 제안 라벨을 먼저 보지 않고 조건과 근거를 판정. 불일치를 보고하고, 치명 사례와 애매한 라벨은 개발 측 검토 후 고정.
3. 사용자 역할 담당: 숨은 사용자 정보를 가지고 질문받은 것만 답함. 실행 결과를 좋게 만들려고 누락 조건을 자발적으로 알려주지 않음.
4. 실행·분석 담당: 고정된 버전의 실제 파이프라인을 실행하고 평가 근거와 실패 위치 기록. 객관적 ID/범위/상태 검사는 코드로 수행.

정답 확정 후에만 제품 모델을 실행한다. LLM 채점은 텍스트 의미 보존 검토의 보조 수단이며 다수결로 정답을 확정하지 않는다. 같은 모델의 여러 에이전트는 같은 오해를 공유할 수 있다. 최종 라벨 이견을 사용자에게 떠넘기지 않고 개발 검토 대상으로 둔다. 합의 불가 사례는 별도 ambiguous 그룹으로 공개하며 유리하게 삭제하지 않는다.

## 6. 단계별 원인 분리와 전체 시험

| 시험 | 입력 | 확인할 결과 |
|---|---|---|
| 의도 확인 | 최초 지시 + 모의 사용자 답변 | 필요한 질문, 확인된 조건 보존, 동의 없는 변경 없음 |
| Jev 변환 | 사전 검토된 최종 텍스트 | 정책 JSON의 범위·부정·예외·값 보존 |
| Jev 분류 | 사전 검토된 정책 + 모의 알림 | 사용자 기준 일치/불일치/불확실 판단 |
| 앱 행동 | 정해진 분류 결과/오류 | 알림·기록·보류·제외와 오류 복구 |
| 전체 | 최초 지시부터 실제 구성요소 연결 | 중요한 알림 도달과 오류 전파 |

정답 중간 결과로 교체하는 검사는 진단용으로만 사용한다. 전체 경로의 실수를 정답 입력으로 덮어쓴 결과를 원래 실행 성공에 합치지 않는다. 아직 실제 Jev 정책 컴파일러/앱 행동 연결이 없으므로 이를 검증 실행기 안에 구현해야 한다. 모의 구성요소는 명시하고 실제 구성요소 통과와 구분한다.

## 7. 단순 예문을 넘는 시험

- 같은 알림/반대 정책: 패배 결과를 ‘모든 결과’에는 알림, ‘승리만’에는 제외. 일반 중요도가 아니라 사용자 기준을 따르는지 검사.
- 같은 뜻/다른 표현: 문장 순서·별칭·오타·구어체가 바뀌어도 의미 유지.
- 조건 한 개 변경: 팀·채널·발신자·앱·예외만 바꿔 관련 결과만 달라지는지 검사.
- 시간순: 예고→경기 중→최종→정정, 미납→완료→처리 실패. 미래 문맥은 입력하지 않음.
- 조건 수정: 추가·부분 교체·예외·충돌·수정 취소·이전 버전 재개. 기존 기준 보존 검사.
- 데이터 결손: 잘린 메일, 이름 없는 방, 채널명 미제공, 사진만 있는 알림, 문맥 만료.
- 시스템 실패: API 타임아웃·불완전 JSON·잘못된 ID·앱 종료·중복·순서 역전·권한 해제.
- 공격성 입력: 알림 본문이 정책 변경 명령처럼 보이는 경우. 명령과 관찰 데이터를 구분.

## 8. 제안 규모와 분할

모든 숫자는 제안치이며 이미 확보한 사례 수가 아니다.

- 준비: 기존 20개와 실패 사례는 개발 회귀용으로 고정. 사례 형식·실제 정보 범위·채점 계약부터 확정.
- 파일럿: 미국/영국 각 20개, 총 40개 지시 설정 과정 × 12개 모의 알림 = 480개 알림 판단. 12영역을 포함하고 전체 경로 연결·정답 품질·비용을 먼저 측정.
- 본평가: 미국/영국 각 120개, 총 240개 독립 지시 설정 과정 × 12개 모의 알림 = 2,880개 알림 판단. 각 영역 최소 10설정 확보하고 나머지는 상위 앱 우선 배분.
- 12알림은 초기 설계상 알려야 함 5 / 명확한 비대상 4 / 정보부족 3을 기본으로 하되 사건 논리가 우선이다. 이 비율은 실사용 빈도가 아니다. 미지원 설정은 정책을 강제 생성하지 않고 ‘미적용’ 기대 행동으로 평가한다.
- 의미/시나리오 가족 단위로 개발 120 / 검증 60 / 봉인 60설정을 분할한다. 같은 시나리오의 표현 변경·반대 정책·후속 사건은 같은 분할에 둔다. 가족 크기가 다르면 수치보다 누출 방지를 우선해 실제 개수를 보고한다.
- 48설정을 위험·영역별로 사전 선정해 총 3회씩 반복(기본 실행 외 96설정 추가). 반복은 새 사례 수에 넣지 않는다. 반복 결과 중 잘된 것만 고르지 않는다.
- 봉인셋을 열어 원인을 개선에 사용하면 회귀셋으로 이동하고 새 평가셋을 준비한다. 개선 후 같은 봉인셋 점수만으로 일반화를 주장하지 않는다.

초기 산정상 설정당 LLM 평균 3회라면 본평가 기본분은 약 720 LLM 호출 + 최대 240 Jev 정책 변환 + 최대 2,880 Jev 분류 호출이다. 이는 검토·생성 에이전트, 반복 시험, 정답 중간 결과를 넣는 진단, 재실행 비용 제외다. 먼저 10개 파일럿으로 각 비용을 측정하고 실행기에서 최대 호출 수·총 비용 한도·중단 조건을 설정한다. 현재 가격을 검증하지 않은 상태에서 총 달러 비용을 약속하지 않는다.

### 2026-09-23 실행 범위 조정

위 480개 전체 경로 파일럿은 원래 제안이다. 현재 정책 JSON 컴파일러가 아직 없어, 사용자의 테스트 시작 요청에는 **기존 구현의 단계별 기준선**을 먼저 실행한다. 영어24/한국어12/혼용4의 지시40개, 이 중 명확한 지시32개 × 12알림 = 고유 알림384개다. 나머지8개는 질문·대기·미지원의 첫 응답을 검사한다. 정답 원문과 LLM 정리문을 별도 Jev 요청에 넣으므로 최대768회 분류이며 768개 독립 사례는 아니다. 기존 v3 프롬프트·기대값·임계값과 소스 해시를 실행 전 고정한다.

이 기준선은 국가별 대표성, 다회차 설정 완료, 정책 JSON 의미 보존, 실기기 표시를 검증하지 않는다. [독립 검토](evaluation-integrity-pilot-v1.md), [실행 결과](../evaluations/reliability-pilot-v1/REPORT.md). 이후 전체 경로 평가와 본평가의 미완료 항목은 그대로 남는다.

## 9. 성공 기준과 개선 절차

다음은 첫 품질 기준 제안이며 성능 달성 주장이 아니다. 실행 전에 분모·기대 행동·임계값을 고정한다.

- 치명 불변 조건: 미완성 기준 활성화, 동의 없는 숨김 범위 확대, 다른 방/계정 연결, 확실히 알려야 할 고위험 알림의 조용한 제외/삭제는 필수 회귀셋에서 0건. 발견 시 다음 제품 연결 단계 보류.
- 최종 적극 알림 도달률: 기대가 ‘즉시 알림’인 사례 중 실제 알림 결정 비율. 목표안 99% 이상. 보류·조용한 기록·오류로 멈춤은 성공이 아니다. 앱 실제 표시 미연결이면 모의 행동 결과로만 표기.
- 의미 보존: 확인된 조건의 누락/추가/반전, 최종 완료 오판을 건수와 설정 단위로 보고. 중간 JSON이 틀렸는데 우연히 최종 판단만 맞은 경우도 기록.
- 보류율·과잉 알림률·정상 설정 완료율·불필요한 질문 수를 함께 보고한다. 모두 보류하거나 전부 알리는 방식으로 누락 점수를 높이지 못하게 한다. 수치 상한은 파일럿의 실제 분포를 검토한 뒤 본평가 전에 고정한다.
- 미국/영국·앱·영역·정보 완전성·위험도별 분자/분모와 실패 목록을 공개한다. 전체 평균으로 납부 영역 실패를 가리지 않는다. 일부 영역의 표본 부족은 통과가 아닌 추가 검증으로 남긴다.
- 무오류 보장은 하지 않는다. 합성 2,880건은 설계 범위 안의 증거다. 실제 발생확률/백만 건당 누락률로 환산하지 않는다. 반복 입력은 독립 표본이 아니다.

개선은 오류 위치에 따라 수행한다: 상태 누락→저장/전달 수정, 미지원 오해→기능 계약 수정, 대안 자동 전환→수락 단계 추가, 문맥 오해→원칙 프롬프트/모델 비교, 정책 손실→Jev 변환 검사, 확정 앱/방 범위 오류→코드 검증. 한 변경씩 동일 개발/검증셋으로 비교하고 원래 실패 기록을 유지한다. 모델 비교도 같은 조건으로 진행하며 저렴하다는 이유로 필수 품질 기준을 낮추지 않는다.

## 10. 합성 검증 이후

대표 앱별 Android 알림이 실제로 어떤 필드를 제공하는지 Galaxy에서 확인한다. 공식 도움말만으로 실제 본문 형식을 검증 완료로 간주하지 않는다. 이후 사용자 허용 범위에서 비식별 사례를 검토하고, 원본 알림을 숨기지 않는 관찰 모드로 수집/분류/표시의 누락 원인을 비교한다. 의미 판정이 통과해도 원본 앱이 알림을 내지 않으면 수집할 수 없다는 한계를 별도 안내한다.

다음 구체 작업은 앱 UI 확대가 아니라 (1) 통계 근거가 붙은 앱 목록 확정, (2) 독립 정답이 있는 영어 파일럿 40설정 작성, (3) 전체 경로 실행기 연결, (4) 실패 원인별 개선이다. 단기 일정은 고정 약속하지 않고 첫 파일럿에서 정답 검토 시간과 실제 호출량을 측정해 산정한다.
