# Policy JSON Validation — 개발 계약

후속 앱 구현: [정책 검증 연결 및 실제 검사 기록](STRUCTURED_POLICY_IMPLEMENTATION.md). 의미 검증 응답의 질문 없음은 현 구현에서 빈 문자열로 표현하며 세 가지 상태의 의미는 동일하다.

2026-09-24 사용자 추가 지시를 반영한다. [AI 역할 결정](AI_ROLE_DECISION.md) 및 [정책 모델 범위](POLICY_MODEL_SETTINGS_SCOPE.md)에 적용한다. 구현 예정 계약이며 현재 설치 앱에 새 검증 파이프라인이 연결됐다는 뜻은 아니다.

## 저장 전 흐름

```text
사용자 지시 + 기존 정책
→ OpenAI policy editor
→ strict Structured Output JSON
→ 앱 결정론적 검증 + 이전/제안 정책 비교 + 위험 분류
   ├─ 구조/참조 등 확정 오류 → 적용 차단, 초안 오류 표시
   ├─ 위험 없음 → 사람이 읽는 Diff → 사용자 확인 → 원자적 저장
   └─ 의미 위험 있음 → OpenAI semantic validator
       ├─ valid → Diff → 필요한 사용자 확인 → 원자적 저장
       ├─ invalid → 정확한 문제 표시, 수정 초안으로 유지
       └─ clarification_required → 질문/선택 → 답변 반영 → 처음부터 재검증
```

위험 없는 사소한 직접 토글은 별도 확인을 생략할 수 있다. 의미 있는 자연어 변경은 Diff 확인을 거친다. 검증 실패·응답 없음·취소 시 기존 활성 정책을 유지한다. 미검증 제안은 미활성 초안으로만 보관하며 실행 정책 저장소와 구분한다. Jev는 이 흐름에 관여하지 않고 저장된 규칙에 대한 알림 일치 판단만 한다.

## 1. 스키마 검증

OpenAI Structured Outputs의 strict JSON Schema를 사용한다. 지원되는 경우 자유 형식 JSON mode로 대체하지 않는다. 앱에서도 같은 계약으로 검증한다.

- 허용 scope type, condition/event type, action, exception 구조, Boolean enabled, 변경 operation을 제한한다.
- 변경 operation은 ADD / UPDATE / DELETE / REPLACE / SET_ENABLED의 명시적 허용 목록으로 시작하며 신규 값은 스키마 버전 변경 없이 받지 않는다.
- 모든 객체에서 추가 필드를 금지하고 필수 필드·자료형·중첩 구조·배열/문자열 상한을 검사한다. 모델 응답의 거절·잘림·불완전 결과도 적용하지 않는다.
- 알 수 없는 필드나 enum은 버리거나 UNKNOWN으로 바꿔 활성화하지 않고 거부한다. 런타임 알림 의미 판단의 UNKNOWN과 정책 편집 JSON의 허용되지 않은 enum을 구별한다.
- 실제 대상 식별자와 정책 revision은 앱 소유다. 모델이 만든 식별자를 실제 대상이라고 인정하지 않는다. 신규 정책의 임시 ID는 검증 후 앱이 정식 ID로 부여한다.

## 2. 결정론적 검증과 위험 감지

앱은 모델이 제출한 변경 목록만 믿지 않고 이전 JSON과 제안 JSON으로 실제 Diff를 계산한다. operation과 실제 Diff가 다르면 차단한다.

| 검사 | 처리 |
|---|---|
| 미허용 값, 필수 필드 누락, 타입 불일치 | 차단 |
| 존재하지 않는 정책/앱/대화/발신자/부모 참조 | 차단 또는 실제 대상 재선택; 범위를 넓혀 대체하지 않음 |
| 좁은 Scope → ALL_APPS 또는 대상/필터 제거 | 확대 위험으로 분류, 요청 근거 확인 |
| 기존 규칙 삭제/대체, enabled 변경 | 실제 변경 ID와 요청 대상 비교; 요청되지 않은 변경 차단 |
| 같은 Scope에서 같은 조건에 상반된 Action | 충돌 감지; 명시적 예외/우선순위로 해결되지 않으면 보완 |
| 부모 범위 밖 예외, 없는 부모, 순환 참조 | 차단; 무관한 정책을 덮어쓰지 않음 |
| 요청 범위 밖 HIDE/QUIET/WATCH 추가·확대 | 차단 또는 의미 재확인; 자동 적용 금지 |
| 이번 요청과 무관한 정책 변경 | 변경 사실 탐지 후 허용된 편집 대상과 비교; 무단 변경 차단 |

직접 편집에서는 사용자가 선택한 정책 ID·동작·범위가 요청 근거다. 자연어에서 ‘사용자가 정말 삭제를 원했는가’, ‘두 조건의 의미가 같은가’는 코드만으로 완전히 입증할 수 없다. 편집 모델의 자기 신고를 결정론적 근거로 사용하지 않는다. 근거가 불명확하면 위험으로 올리고 별도 의미 검증/질문으로 해결한다. 충돌도 구조상 판정 가능한 것과 의미 해석이 필요한 것을 구분한다.

## 3. 위험 기반 의미 검증

추가 LLM 검증은 다음 위험이 있을 때만 수행한다. 기본 편집마다 무조건 두 번째 호출을 하지 않는다.

- 기존 규칙 삭제
- Scope 확대(ALL_APPS 전환 외 대상 추가·제약 제거 포함)
- 새 HIDE, 기존 HIDE 활성화 또는 숨기는 대상 증가
- 새 예외 또는 부모/예외 의미 변경
- 충돌 규칙
- 여러 정책 대체
- 모호한 지시 또는 해석 확신 부족
- 요청하지 않은 축소/동작 변경 가능성, 중요한 SHOW/예외 비활성화 등 중요한 알림을 놓칠 수 있는 변경

위험 판정은 앱 Diff와 검증 결과를 포함하며 모델의 ‘위험 없음’ 주장으로 생략하지 않는다. 확신 부족은 사용자 의미 미해결 등 근거로 판단하고 모델이 만든 수치를 보정된 정확도로 취급하지 않는다.

독립된 검증 요청에 이전 정책 JSON, 사용자 새 지시(관련 보충 답변 포함), 제안 정책 JSON을 전달한다. 필요하면 앱이 계산한 Diff·문제 경로·지원 범위를 함께 전달하고 알림 원문은 기본 포함하지 않는다. 검증자는 규칙을 다시 쓰거나 저장하지 않고 결과와 정확한 문제만 반환한다.

검사 내용: 사용자 의미 보존, 무단 추가/삭제, 잘못된 확대/축소, 예외 표현, 기존 규칙 충돌, 합리적인 복수 해석 여부. 애매하면 추측하지 않고 질문한다.

검증 응답도 strict schema를 사용하며 아래 필드는 항상 포함한다. 질문이 없을 때 clarification_question은 null이다.

```json
{
  "valid": false,
  "issues": [
    {
      "code": "AMBIGUOUS_SCOPE",
      "policy_id": "policy_001",
      "path": "/policies/0/scope",
      "message": "회사 전체와 특정 단톡방 중 적용 대상 확인이 필요합니다."
    }
  ],
  "needs_user_clarification": true,
  "clarification_question": "회사 알림 전체를 숨기고 일정 변경만 보겠다는 뜻인가요, 아니면 회사 단톡방에만 적용할까요?"
}
```

issues의 code도 허용 목록으로 제한한다(SCHEMA_ERROR, INVALID_REFERENCE, UNREQUESTED_ADDITION, UNREQUESTED_DELETION, SCOPE_EXPANSION, SCOPE_NARROWING, EXCEPTION_MISMATCH, CONFLICT, UNRELATED_CHANGE, AMBIGUOUS_SCOPE, AMBIGUOUS_INSTRUCTION, UNSUPPORTED_ACTION). 필수 의미 불변식:

- valid: valid=true, issues=[], needs_user_clarification=false, clarification_question=null.
- invalid: valid=false, issues에 정확한 문제 포함, needs_user_clarification=false.
- clarification_required: valid=false, needs_user_clarification=true, 비어 있지 않은 질문. 사용자 예시처럼 issues=[]도 허용한다.
- 상충하는 플래그·없는 정책에 대한 임의 판정·잘못된 응답은 통과로 해석하지 않는다.

확정된 코드 검증 실패를 LLM의 valid가 무효화할 수 없다. 수정이나 답변으로 제안이 달라지면 다시 검증한다. 네트워크 오류·거절·타임아웃은 검증 미완료로 남기고 반복 무제한 재시도하지 않는다.

## 4. 확인과 저장

Diff는 실제 저장할 검증 완료 JSON에서 만들어 추가/변경/삭제와 유지 내용을 보여준다. 적용 범위, 동작, 예외의 변화가 읽혀야 한다. 위험 검증의 valid는 사용자 승인과 다르다.

중요 알림을 숨길 수 있는 변경에는 확인을 요구한다. 토글이라도 HIDE 켜기, SHOW 예외 끄기, Watch 끄기 등 영향에 따라 확인한다. 매번 의미 없는 확인창을 띄우지는 않는다. 코드가 생성한 명확한 직접 조작은 규칙을 OpenAI로 재작성하지 않지만, 위 위험에 해당하면 별도 의미 검증과 필요한 확인을 생략하지 않는다.

검증·Diff·확인은 동일한 base revision과 proposal hash에 연결한다. 확인 후 JSON이나 활성 버전이 바뀌면 승인 재사용을 금지하고 재검증한다. 저장은 원자적으로 수행하고 실패하면 이전 버전을 유지한다. 불확실성이 남은 HIDE 범위 확대나 기존 규칙 삭제는 조용히 적용하지 않고 사용자에게 묻는다.

## 5. 구현 순서와 검증 기준

정책 모델 A에서 schema/operation/위험/응답 계약을 고정하고 B에서 초안·revision·원자적 저장을 연결한다. E에서 결정론적 검증 → 위험 분기 → OpenAI 의미 검증/질문을 연결하고 D/F에서 위험별 확인·Diff를 검증한다. 전체 신뢰성 평가와 Galaxy 검증 전 완료로 기록하지 않는다.

필수 사례:

- 잘못된 enum/추가 필드/없는 ID는 LLM을 호출해 구제하지 않고 차단.
- 위험 없는 단순 변경은 추가 의미 검증 0회; 위험 변경은 검증 누락 없음.
- 단톡방 HIDE가 ALL_APPS로 바뀜, 요청 없는 삭제, 무관한 규칙 변경은 적용되지 않음.
- 명시적으로 요청한 삭제/범위 확대도 의미 검증·필요한 Diff 확인 후에만 저장.
- 새 예외·다중 대체·구조/의미 충돌·다의적 한국어/영어는 각 분기로 처리.
- 위험한 토글과 사소한 토글의 확인 정책 구별.
- 검증 응답 오류·API 실패·화면 이탈·재시작·검증 후 수정·오래된 승인으로 기존 정책 손실 없음.
- 기본 분류 경로의 OpenAI 0회, 정책 작성/검증 경로의 Jev 0회.

편집 호출과 의미 검증 호출의 수·입력량·지연·예상 비용을 구분하고 위험 검출 누락, 잘못된 통과/차단, 질문 부담, 중요한 알림의 false suppression을 기록한다. 테스트는 아직 실행하지 않았다.

## 온보딩 입력 연결

[첫 온보딩](FIRST_ONBOARDING_SCOPE.md)도 동일한 저장 전 검증을 사용한다. 추천 항목 선택·자연어·앱별 처리의 모순과 무단 제외를 검사한다. Time Condition은 허용 필드·시간대·날짜/구간·만료 동작을 검증하며 시간 제약 삭제나 기간 확대도 Scope 확대와 같은 위험으로 취급한다. 미해결 시간 조건을 빼고 영구 HIDE로 저장하지 않는다.
