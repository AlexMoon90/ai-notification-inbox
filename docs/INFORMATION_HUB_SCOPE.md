# 알림정보허브 앱 — 화면구조 및 기능 재정의 수정안

## 1. 앱의 성격 재정의

이 앱을 단순한 알림 저장/차단 앱으로 만들지 않는다.

핵심 목적은 다음과 같다.

**스마트폰에 흩어져 들어오는 알림을 의미에 따라 다시 정리하여, 사용자가 지금 알아야 할 것과 대화의 흐름, 나중에 찾아볼 생활정보를 각각 적절한 공간에 보여주는 개인 정보 허브**

기존 알림 앱처럼 앱별 알림 목록이나 단순 보관함 중심으로 설계하지 않는다.

알림의 출처보다 **알림이 의미하는 내용과 사용 목적**을 우선한다.

---

# 2. 하단 Navigation 구조

기존 하단 메뉴를 다음 3개로 수정한다.

1. **Now**
2. **메신저**
3. **분류함**

`알림 기준`은 별도 하단 메뉴에서 제거한다.

알림 기준은 `Now` 화면 내부에서 접근하도록 변경한다.

---

# 3. Now

## 정의

**지금 사용자가 알아야 할 알림만 골라서 보여주는 화면**

전체 알림 기록을 보여주는 타임라인이 아니다.

사용자가 설정한 기준에 따라 실제로 알림을 받을 가치가 있다고 판단된 항목만 보여준다.

Now에 표시되는 알림이 반드시 특정 이벤트 유형을 가져야 하는 것은 아니다.

일반적인 중요한 알림도 사용자 정책에 따라 Now에 표시될 수 있다.

---

## Now 화면 UI

큰 카드형 UI는 피하고, 한 화면에서 여러 알림을 빠르게 훑을 수 있도록 **컴팩트한 리스트형 UI**를 사용한다.

### 기본 정보 구조

모든 Now 항목의 기본 정보는 다음 세 가지다.

1. **제목**
2. **내용**
3. **출처 + 시간**

예:

**○○카드 이용 안내**
32,500원이 승인되었습니다.
신한카드 · 12분 전

또는:

**친구모임방**
이번 주 토요일 저녁 괜찮으세요?
KakaoTalk · 5분 전

즉 `이벤트 종류`가 기본 제목을 대신하지 않는다.

원본 알림 제목과 내용을 사용자가 바로 파악할 수 있는 것이 우선이다.

---

## 이벤트/상태 강조

Jev 또는 대화 문맥 분석을 통해 명확한 의미 있는 상태가 감지된 경우에만 별도의 강조 요소를 추가한다.

예:

`답변 필요`

**친구모임방**
토요일 참석 가능 여부를 묻고 있습니다.
KakaoTalk · 5분 전

또는:

`약속 확정`

**친구모임방**
토요일 오후 7시 · 강남역
KakaoTalk · 12분 전

또는:

`배송 지연`

**오늘 도착 예정이던 상품의 배송이 지연되었습니다.**
Coupang · 25분 전

이벤트/상태는 다음과 같이 처리한다.

- 작은 Badge 또는 Highlight Label 형태
- 제목보다 시각적으로 과도하게 크지 않게 표시
- 의미 있는 상태가 있을 때만 표시
- 상태가 없는 일반 Now 항목에는 해당 영역 자체를 표시하지 않음
- 빈 공간이나 `일반 알림` 같은 의미 없는 라벨을 만들지 않음

즉 화면의 기본 구조는 항상:

**제목 → 내용 → 출처/시간**

이며,

특별한 의미가 감지된 경우:

**[이벤트 강조] + 제목 → 내용 → 출처/시간**

형태가 된다.

## 구조화된 핵심 정보

날짜, 시간, 장소, 금액 등 사용자가 바로 확인할 가치가 있는 구조화 정보가 존재하는 경우 내용 영역에서 강조할 수 있다.

예:

`약속 확정`

**친구모임방**
**9월 30일 · 오후 7:00 · 강남역**
KakaoTalk · 12분 전

이 경우에도 이벤트 라벨 자체보다 실제 날짜·장소 등의 정보가 더 중요하다.

---

## Now UI 원칙

Now는 이벤트 대시보드가 아니라 **사용자가 선택한 중요한 알림 스트림**이다.

따라서 다음 원칙을 따른다.

- 이벤트 종류를 모든 항목에 강제로 부여하지 않는다.
- 원본 제목과 핵심 내용이 항상 기본 정보다.
- 이벤트가 발견되었을 때만 보조적으로 강조한다.
- 한 화면에서 많은 항목을 빠르게 확인할 수 있도록 높이를 최소화한다.
- 불필요한 큰 카드, 많은 여백, 반복되는 설명을 피한다.
- 중요한 이벤트가 있는 항목과 일반 Now 항목의 차이가 자연스럽게 보이도록 한다.

---

## 알림 기준

Now 상단 우측에 `알림 기준` 또는 적절한 설정 아이콘을 배치한다.

알림 기준 화면은 현재 개발 중인 정책 관리 UI로 연결한다.

사용자가 자연어로 다음과 같이 기준을 추가/수정할 수 있어야 한다.

예:

`내가 답해야 할 때 알려줘.`

`일정이 바뀌면 알려줘.`

`쿠팡 광고는 숨기되 배송 알림은 보여줘.`

알림 기준은 별도의 하단 Navigation 항목으로 만들지 않는다.

---

# 4. 메신저

## 정의

**문자 및 여러 메신저 앱에서 들어온 알림을 서비스 → 대화방 → 메시지 구조로 다시 정리해서 보여주는 화면**

일반 알림처럼 메시지를 낱개로 나열하지 않는다.

메신저 데이터의 기본 구조는 다음과 같이 한다.

`Message Service → Conversation Room → Messages`

여기서 Message Service에는 다음이 포함될 수 있다.

- 문자(SMS/RCS)
- KakaoTalk
- WhatsApp
- Instagram DM
- Telegram
- Facebook Messenger
- 기타 메시징 앱

---

## 문자 처리 원칙

문자는 메신저 화면의 기본 소스 중 하나로 취급한다.

특정 앱 이름인 `Google Messages`, `Samsung Messages` 등을 UI에 고정하지 않는다.

사용자 기기, 국가, 제조사, 통신사에 따라 실제 기본 문자 앱은 달라질 수 있으므로 UI에서는 논리적으로 모두 **`문자`** 로 묶는다.

즉 상단 탭은 예를 들어:

`전체 | 문자 | KakaoTalk | WhatsApp | Instagram | Telegram`

형태로 구성한다.

내부적으로 실제 Notification을 발생시킨 패키지와 메타데이터는 저장하되, 사용자에게는 필요 이상으로 문자 앱 제품명을 노출하지 않는다.

---

## 메신저 앱 탭

화면 상단에 실제로 알림이 수집된 메시징 서비스를 탭 형태로 표시한다.

예:

`전체 | 문자 | KakaoTalk | WhatsApp | Instagram | Telegram`

문자는 기본 메시지 소스로 우선 고려한다.

설치된 모든 앱을 강제로 표시하지 않는다.

실제로 대화형 알림이 들어온 앱을 기준으로 탭을 동적으로 생성한다.

앱 수가 많아지면 가로 스크롤이 가능하도록 한다.

---

## 대화방 목록

각 메시징 서비스 탭을 선택하면 대화방 단위로 보여준다.

예:

### 문자

- 엄마
- ○○병원
- 010-1234-5678
- ○○카드
- 배송안내

### KakaoTalk

- 회사 프로젝트방
- 친구 모임방
- 가족방
- 김민수
- 고객 상담방

각 대화방 항목에는 가능하면 다음을 표시한다.

- 대화방 또는 연락처 썸네일
- 대화방 이름 또는 발신자 이름
- 최근 메시지
- 마지막 메시지 시간
- 누적/미확인 메시지 수

문자의 경우 연락처 정보가 있으면 연락처 이름을 우선 사용하고, 없으면 발신번호 또는 발신자 문자열을 표시한다.

개인톡과 단체방을 별도의 메뉴로 강제 분리하지 않는다.

대화방 썸네일과 이름만으로 사용자가 충분히 성격을 판단할 수 있으므로 업무/친구/취미/스터디 등의 추가 카테고리 입력을 요구하지 않는다.

---

## 대화방 상세

대화방을 선택하면 알림으로 수집된 메시지를 최신순(최신 메시지가 위)으로 보여준다. (2026-09-27 사용자 수정 요청)

그룹방은 반드시 다음 구조로 표시한다.

`대화방 → 개별 메시지 → 메시지 발신자`

그룹방의 각 사람을 별도의 대화방으로 만들지 않는다.

예:

### 회사 프로젝트방

민수
`내일 미팅 시간을 변경해야 할 것 같습니다.`

지영
`저는 오후 3시 가능합니다.`

팀장
`그럼 오후 3시로 변경하겠습니다.`

문자 역시 발신자 또는 연락처 단위의 대화 흐름으로 보여준다.

예:

### ○○병원

`9월 28일 오후 2시 진료 예약이 완료되었습니다.`

`방문 전 문진표를 작성해주세요.`

이 두 메시지는 개별 알림으로 흩어놓지 않고 동일 발신자 대화 흐름에 연결한다.

---

## Conversation 식별

가능하면 Notification이 제공하는 다음 메타데이터를 활용한다.

- conversation shortcut
- shortcutId
- notification title
- sender
- people/person metadata
- package name
- notification channel
- 기타 conversation 관련 metadata

단, 모든 메시징 앱 또는 문자 앱이 동일한 메타데이터를 제공한다고 가정하지 않는다.

필요한 경우 다음 정보를 조합하여 Conversation을 식별하는 fallback 로직을 둔다.

- source package
- title
- sender
- conversation title
- phone number
- shortcutId

Conversation 식별 결과가 불확실한 경우 서로 다른 대화를 무리하게 하나로 합치지 않는다.

---

## 원래 앱 연결

Notification의 `contentIntent`, conversation shortcut, deep link 등이 제공되는 경우 가능한 범위에서 저장하거나 참조한다.

대화방 상세 또는 메시지 상세에서:

`원래 앱에서 열기`

기능을 제공한다.

정확한 대화방 deep link가 불가능한 경우 최소한 해당 원본 앱을 실행한다.

문자 역시 가능한 경우 기본 문자 앱의 해당 대화로 이동하고, 불가능한 경우 문자 앱 자체를 실행한다.

# 5. 대화 문맥 추적

대화방 상세 화면에서 사용자가 원하는 방에 대해서만 문맥 추적 기능을 활성화할 수 있도록 준비한다.

초기 MVP에서 모든 대화방을 AI로 분석하지 않는다.

사용자가 추적 대상으로 선택한 대화방에 대해서만:

- 내가 직접 언급됨
- 답변이 필요함
- 일정이 결정됨
- 일정이 변경됨
- 장소가 결정됨
- 비용 또는 회비 요청
- 중요한 결정이 발생함

등의 의미 변화를 추적할 수 있도록 구조를 준비한다.

문자 대화도 필요하다면 동일하게 문맥 추적 대상으로 선택할 수 있어야 한다.

의미 있는 변화가 발생하면 해당 이벤트를 `Now`로 전달한다.

예:

친구모임방 대화 여러 개

→ 최종적으로 토요일 오후 7시 강남역 확정

→ Now:

`약속 확정`

**친구모임방**
토요일 오후 7시 · 강남역
KakaoTalk · 방금

# 6. 분류함

## 정의

**여러 앱과 문자에서 들어온 알림을 출처가 아니라 정보의 의미에 따라 다시 정리하는 화면**

단순한 알림 저장소가 아니다.

예를 들어 예약 정보가:

- 문자
- KakaoTalk
- 호텔 앱
- 이메일 알림

중 어디에서 왔든 모두 `예약` 카테고리에서 확인할 수 있어야 한다.

# 8. 문자 및 메신저와 분류함의 관계

문자나 메신저 알림이라고 해서 메신저 화면에만 존재하는 것은 아니다.

동일한 메시지가 생활정보 성격을 가지면 분류함에도 연결할 수 있다.

예:

문자:

`○○호텔 9월 30일 오후 7시 예약이 확정되었습니다.`

→ 메신저 > 문자 > ○○호텔 대화방

동시에:

→ 분류함 > 예약

또 다른 예:

문자:

`신한카드 32,500원 승인`

→ 메신저 > 문자 > 신한카드

동시에:

→ 분류함 > 금융

즉:

**메신저 = 대화/발신자 흐름**

**분류함 = 정보의 의미**

로 역할을 분리한다.

---

# 9. SNS 처리 원칙

SNS 앱 전체를 하나의 종류로 처리하지 않는다.

같은 앱에서도 알림 성격에 따라 다른 화면으로 보낼 수 있어야 한다.

예:

Instagram DM
→ 메신저

Instagram 좋아요 / 댓글 / 팔로우
→ 분류함 > SNS

Facebook Messenger 대화
→ 메신저

Facebook 게시물 댓글 / 그룹 활동
→ 분류함 > SNS

즉 앱이 아니라 **Notification Event Type 기준으로 라우팅한다.**

# 10. 동일 알림의 다중 연결

하나의 원본 알림이 여러 화면에서 다른 역할로 표시될 수 있다.

예:

KakaoTalk 단톡방:

`토요일 오후 7시 강남역으로 확정`

이 메시지는:

### 메신저

친구모임방의 원본 메시지 흐름에 존재

### Now

`약속 확정` 상태가 강조된 중요 알림으로 표시 가능

### 분류함

필요한 경우 일정/예약 성격의 정보로 연결 가능

문자도 동일한 원칙을 적용한다.

중요:

원본 알림 데이터를 각 화면마다 중복 저장하지 않는다.

하나의 원본 Notification Entity를 기준으로:

- Now Event
- Conversation Message
- Classified Item

등이 Reference를 가지는 형태로 설계한다.

---

# 11. AI 역할 분리

## Jev

고빈도 실시간 판단에 사용한다.

주 역할:

`이 알림이 어떤 종류의 이벤트인가?`

예:

- RESERVATION
- DELIVERY
- PAYMENT
- MONEY_RECEIVED
- ORDER
- REFUND
- SOCIAL_ACTIVITY
- REPLY_REQUIRED
- SCHEDULE_CHANGE
- MEETING_CONFIRMED
- AI_TASK_COMPLETED
- AI_INPUT_REQUIRED

단, 모든 Now 알림이 반드시 위 이벤트 타입 중 하나로 표시되어야 하는 것은 아니다.

Jev의 이벤트 판단은 분류와 강조에 사용되는 메타데이터이며, 원본 알림 제목/내용을 대체하지 않는다.

가능하면 다음과 같은 구조화 필드도 반환한다.

- confidence
- date
- time
- amount
- currency
- place
- status
- sender
- source type

알 수 없는 값은 임의로 생성하지 않는다.

---

## 앱 코드

Jev 결과를 받아 정책에 따라 직접 라우팅한다.

예:

`DELIVERY`
→ 분류함 / 배송

`SOCIAL_ACTIVITY`
→ 분류함 / SNS

`REPLY_REQUIRED + user policy match`
→ Now에서 `답변 필요` 강조

단순한 분류 및 라우팅에 LLM을 추가로 호출하지 않는다.

---

## LLM

다음과 같이 실제 언어 이해가 필요한 경우에만 사용한다.

- 자연어 알림 정책 생성
- 기존 정책 변경 및 병합
- 복잡한 대화 문맥 요약
- 여러 메시지에서 최종 결정 추출
- 애매한 사용자 의도 처리

분류함 단순 라우팅에는 LLM을 사용하지 않는다.

---

# 12. Local Database

앱의 원본 알림 및 메시지 데이터는 **서버 DB에 저장하지 않는다.**

Android Local DB를 기본으로 한다.

권장:

- Room
- Android Keystore 기반 encryption
- 필요 시 SQLCipher 또는 동등한 암호화 방식 검토

로컬 DB에는 다음 데이터를 저장할 수 있도록 한다.

- Notification
- Conversation
- Message
- Now Event
- Classified Item
- Policy
- Source App
- Message Service
- Deep Link / PendingIntent 관련 참조 가능 정보

Conversation은 문자와 일반 메신저를 동일한 상위 모델로 다룰 수 있도록 설계한다.

예:

- serviceType = SMS
- serviceType = KAKAOTALK
- serviceType = WHATSAPP
- serviceType = INSTAGRAM_DM
- serviceType = TELEGRAM

UI에는 필요에 따라 사용자 친화적인 표시명을 사용한다.

# 13. 개인정보 보호 원칙

사용자 알림, 문자, 메시지, 금융/예약 기록은 기본적으로 단말 내부에 저장한다.

외부 AI API를 사용하는 경우:

- 필요한 텍스트만 전송
- 불필요한 과거 데이터를 함께 보내지 않음
- 서버에 장기 저장하지 않음
- 앱 내부 DB와 외부 AI 분석을 명확히 분리

제품의 핵심 신뢰 원칙:

**“알림과 대화 기록은 사용자의 휴대폰 안에 저장한다.”**

---

# 14. 데이터 보관

향후 사용자가 보관 기간을 설정할 수 있도록 DB 설계 시 삭제 시점 필드를 고려한다.

예:

- Now: 기본 30일
- Messenger: 기본 60일
- 분류함: 기본 90일
- 사용자가 고정한 항목: 직접 삭제 전까지 유지

MVP에서는 실제 삭제 정책을 단순하게 시작해도 되지만 향후 카테고리별 보관기간을 다르게 설정할 수 있도록 데이터 구조를 준비한다.

# 15. 구현 우선순위

이번 수정에서는 기능을 한꺼번에 확장하지 말고 다음 순서로 작업한다.

### Phase 1

하단 Navigation을:

`Now / 메신저 / 분류함`

으로 변경

### Phase 2

Now 화면을:

**제목 → 내용 → 출처/시간**

기본 구조의 컴팩트한 리스트 UI로 재구성한다.

이벤트 또는 상태가 존재하는 경우에만 작은 강조 Badge를 추가한다.

### Phase 3

메신저 화면을:

`서비스 탭 → 대화방 → 메시지`

구조로 변경한다.

최소 기본 탭 후보:

`전체 | 문자 | 실제 수집된 메신저 앱들`

문자는 특정 문자 앱 제품명이 아니라 하나의 논리적 `문자` 소스로 처리한다.

### Phase 4

문자 Conversation grouping을 구현한다.

가능하면 연락처/발신번호/알림 메타데이터를 활용해 동일 발신자의 문자를 하나의 대화 흐름으로 묶는다.

### Phase 5

분류함 UI 생성

우선 Mock Data 기반으로:

- 예약
- 배송
- 금융
- 쇼핑
- SNS
- 여행

카테고리를 표시

### Phase 6

현재 Notification 수집 데이터를 각 화면 구조에 연결

### Phase 7

Jev 결과 기반 자동 분류/라우팅 연결

### Phase 8

Conversation Context Tracking 추가

# 16. UI 전체 방향

세 화면의 역할이 한눈에 달라 보여야 한다.

### Now

컴팩트하고 빠른 스캔 중심.

**제목과 내용이 주인공이고, 이벤트 상태는 있을 때만 강조한다.**

### 메신저

문자와 여러 메시징 앱을 실제 메신저처럼 친숙한 대화방 구조로 보여준다.

**문자와 메신저 앱을 모두 ‘대화’라는 동일한 관점으로 다룬다.**

### 분류함

카테고리를 빠르게 탐색하고 필요한 생활정보를 찾는 정보 Organizer

불필요하게 큰 카드와 과도한 설명은 피한다.

사용자가 앱을 열었을 때 다음 세 가지 질문에 바로 답할 수 있어야 한다.

**Now**
“지금 내가 알아야 할 것이 무엇인가?”

**메신저**
“문자와 메신저에서 무슨 이야기가 오갔는가?”

**분류함**
“나중에 찾아볼 정보가 어디에 있는가?”

이 세 가지를 앱의 기본 정보구조로 사용한다.
