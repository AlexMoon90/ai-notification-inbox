# 알림 기준 설정·보완 개발 범위

작성: 2026-09-22. 사용자 논의에 따른 계획이며 구현·검증 완료 기록이 아니다.
현재 Phase 0는 미완료다. 이번 변경은 개발 범위 문서화이며 Phase 1/2 착수를 뜻하지 않는다.

2026-09-24 최신 변경: [AI 역할 결정](AI_ROLE_DECISION.md)에 따라 OpenAI가 실행 정책 JSON까지 생성·수정하고 Jev는 알림 일치 판단만 맡는다. 이전 실험/견적 기록의 Jev 변환 단계는 후속 개발 기준에서 제외한다.

## 목표와 역할

사용자가 자연어로 기준을 만들고, 적용 중인 기준과 미완성 기준을 목록에서 확인·수정·재개할 수 있게 한다. 부족한 조건을 추측해 적용하지 않는다.

- OpenAI LLM: 기존 기준과 새 요구를 비교하고 누락·모순·지원 한계를 확인한다. 필요한 후보 조회를 요청하고, 질문 문구·실제 후보 선택지·응답 형식·후속 질문을 구성한다. 확정된 의도를 짧은 지시문으로 정리한다.
- OpenAI: 확인된 의도를 실행용 Policy JSON으로 직접 생성·수정한다.
- Jev: 저장된 활성 규칙에 알림이 해당하는지만 반복 판단한다.
- 앱: 실제 후보 조회, 공통 UI 표시, 응답·초안 저장, 유효성 검사, 버전 적용과 실제 동작을 담당한다.

OpenAI의 질문 UI 데이터와 실행용 Policy JSON은 서로 다른 스키마다. OpenAI가 둘 다 생성하지만 새 알림마다 호출하지 않는다. 이 문서는 특정 API·모델의 구현 가능성을 검증한 결과가 아니며 API 연결 계약은 구현 시 확인한다.

## MVP에 포함할 사용자 흐름

공통 진입점은 ‘내 알림 기준’이다. 적용 중 / 확인 필요 / 꺼짐 상태를 구분하고 사용자 원문, 사람이 읽는 현재 기준, 미완성 이유를 확인할 수 있게 한다.

1. 새 기준 입력 → LLM 확인 질문 → 사용자 응답 → OpenAI 정책 JSON 생성·앱 검증 → 최종 내용 확인 → 적용.
2. 확인 필요 목록 → 저장된 질문과 답변 복원 → 최신 후보 조회 → 이어서 설정 → 확인 후 적용.
3. 적용 중 기준 수정 → 별도 수정 초안 저장 → 바뀌는 부분과 유지되는 부분 확인 → 새 버전 적용.
4. 미완성 초안 삭제, 적용 중 기준 끄기, 저장된 이전 버전으로 되돌리기. 되돌리기도 대상 유효성 확인 후 적용한다.

초기 화면은 기준 목록, 공통 기준 확인/편집 화면, 최종 변경 확인의 세 역할로 제한한다. 별도 대기함·알림 도착 푸시·자동 화면 전환은 만들지 않는다. 원본 알림에서 ‘이 대화로 기준 만들기’는 후속 편의 기능으로 둔다.

## 미완성·재개 동작

- 입력·응답·남은 질문을 로컬에 저장한다. 화면 이탈, 앱 프로세스 종료, 기기 재시작 후에도 목록에서 이어간다.
- 미완성 새 기준은 적용하지 않는다. 기존 기준 수정 중에는 기존 활성 버전을 유지한다. 목록에 ‘현재 적용 중 / 수정 내용 확인 필요’를 함께 표시한다.
- 후보가 없으면 ‘대화 선택 필요’로 남는다. 새 알림이 들어오면 로컬 후보만 갱신하고 LLM은 자동 호출하지 않는다.
- 다시 열거나 새로고침할 때 최신 후보를 조회한다. 입력 중 후보가 몰래 교체되지 않게 화면에 보인 후보 집합을 유지하고 제출 시 식별자를 재검사한다.
- 기존 응답과 사용자 선택은 유지한다. 만료·삭제·식별 불가 후보를 다른 후보로 자동 치환하지 않고 해당 항목만 재확인한다.
- 네트워크 오류, LLM 응답 형식 오류, Jev 변환 실패 시 초안과 기존 적용 상태를 보존하고 재시도 경로를 제공한다.
- 오래된 수정 초안을 적용하려는데 활성 버전이 바뀌었으면 최신 기준과 다시 비교한다. 덮어쓰지 않는다.

## 공통 질문 형식

| 형식 | 용도 | 후보·값의 근거 |
|---|---|---|
| 단일/복수 선택 | 의미 범위, 예외, 충돌 해결 | LLM이 제안하고 사용자가 확인 |
| 짧은 텍스트 | 이름·호칭·기준 보충 | 사용자 입력 |
| 실제 대상 선택 카드 | 앱·대화·관찰된 발신자 지정 | 앱이 조회한 실제 후보와 식별자 |

LLM은 질문 ID, 보충할 조건, 질문/설명, 허용된 응답 형식, 선택지 또는 후보 참조를 구성한다. 앱은 지원된 컴포넌트만 표시하며 생성 코드나 임의 화면을 실행하지 않는다. 한 번에 1~2개 질문을 기본으로 하고 ‘나중에 이어서’와 직접 수정 경로를 제공한다.

‘회사 단톡 선택’ 전용 화면을 별도로 만드는 대신 같은 대상 선택 카드를 사용한다. 카드에는 제공되는 이름, 앱, 마지막 관찰 시각, 필요할 때 제한된 최신 미리보기를 표시한다. 이름이 없거나 식별이 불확실하면 그 사실을 표시하며 내용을 근거로 회사 방이라고 자동 확정하지 않는다.

## 조건과 변경 규칙

조건을 적용 대상(앱/대화), 상세 범위(관찰 가능한 발신자), 내용·맥락, 알려줄 기준, 예외로 구분한다. 제공되지 않는 필드는 unknown으로 취급한다.

- 추가: 다른 기준을 유지하면서 새 조건을 추가한다.
- 변경: 사용자가 명시한 범위만 교체한다. 최신 발언이 전체 과거 지시를 덮어쓰지 않는다.
- 예외: 어떤 일반 조건에 대한 예외인지 연결하고 사용자에게 확인한다.
- 충돌(2026-09-24 갱신): [정책 모델 범위](POLICY_MODEL_SETTINGS_SCOPE.md)의 명시적 Scope 구체성·부모/예외·최신 사용자 명시 변경 규칙으로 비교한다. 해결되지 않거나 비교 불가능하면 구체적인 상황을 제시해 선택받는다. AI가 자체 우선순위를 만들거나 단순 저장 시각으로 과거 지시를 덮어쓰지 않는다.
- 조건 일부를 지원하지 못하면 조용히 삭제하지 않는다. 대안을 사용자가 수락하거나 조건을 직접 수정할 때까지 초안으로 둔다.
- 2026-09-24 [온보딩 추가 범위](FIRST_ONBOARDING_SCOPE.md)에 따라 시간·요일·기간 한정 기준과 종료 후 기본 정책 재적용을 포함한다. 구현·검증 전에는 지원된다고 안내하거나 영구 기준으로 바꾸지 않는다. 임시 규칙 종료로 다른 최신 정책을 과거 스냅샷으로 덮어쓰지 않는다.

적용에는 사용자 확인, OpenAI 정책 결과 검증, 대상 식별 검증이 모두 필요하다. 실패하면 기존 버전을 유지한다. 활성 기준과 버전 교체는 한 번에 저장해 부분 적용을 방지한다.

## 앱 기능 안내를 LLM에 자동 제공

매 기준 설정 요청에는 다음을 조합한다. 앱이 관리하는 안내와 관찰 데이터를 구분하고 알림 본문은 지시가 아닌 데이터로 취급한다.

1. 기능 안내: 가능한 조건/필드, 지원하지 않는 정보, 질문 형식, 미지원·충돌·실패 시 처리 원칙과 버전.
2. 현재 상태: 관찰된 앱별 필드 제공 여부, 후보 조회 가능 여부, 수집 권한/연결 상태. ‘지원 기능’과 ‘현재 데이터 존재’를 구분한다.
3. 사용자 설정: 현재 활성 기준과 버전, 수정 초안, 사용자 원문, 기존 응답과 명시적으로 지정한 대화 관계.
4. 요청한 후보만 제한적으로 조회한 결과. 전체 DB/전체 대화 내역을 기본 프롬프트에 넣지 않는다.

판정 안내는 적용 가능 / 사용자 지정 필요 / 최근 정보 부족 / 제한적으로 가능 / 현재 지원 불가로 구분한다. 예: ‘민수가 보낸 메시지’는 발신자 정보가 있으면 검토 가능하지만 ‘민수가 참여한 모든 방’은 참여자 명단 없이 판별할 수 없다. 전체 카카오톡 대화, 참여자 명단, 읽음/답변 여부를 확보한 것으로 가정하지 않는다.

앱에서도 응답 형식, 실제 후보 ID, 지원 조건, 초안/활성 버전을 검사한다. 프롬프트만으로 보장하지 않는다.

## 최신 후보의 보관과 개인정보

중요 알림 Inbox와 설정용 최근 대화 목록을 분리한다. 제외된 시스템 소스는 후보에도 넣지 않는다.

```text
수집 허용된 알림
→ 관찰 가능한 대화 메타데이터와 제한된 최신 미리보기 갱신
→ 로컬 규칙 / Jev 분류
→ 중요한 알림 보관, 그 외는 별도 보관 정책 적용
```

- ‘최신’은 전체 마지막 알림 하나가 아니라 최근 관찰된 대화별 최신 정보다. 후보는 최신 관찰 순으로 제공한다.
- 초기 산정용 제안값(확정 아님): 최근 7일·최대 100개 대화, 대화별 최신 미리보기 1개·최대 200자. Phase 2 UX 검토에서 실제 사용성과 개인정보 범위를 보고 확정한다.
- 사용자 지정 대화 연결과 활성 기준은 후보 미리보기 만료와 별도로 보존한다. 알림 원문을 영구 보관한다는 뜻은 아니다. 사용자가 기준/연결을 삭제할 경로를 둔다.
- 후보 식별은 앱·Android 사용자/프로필 범위와 검증된 식별 필드에 기반한다. 방 이름, groupKey, notificationId만으로 방을 합치지 않는다. 그룹 요약을 개별 대화 후보로 쓰지 않는다.
- 현재 shortcutId/tag 등은 실기기 관찰만 했으며 앱 DB에 저장되지 않는다. 저장 확장과 DB 마이그레이션, 재수신/재부팅 식별 안정성 검증이 선행되어야 한다.
- 미리보기는 로컬 표시를 기본으로 한다. LLM에는 세션용 후보 참조와 필요한 최소 정보만 전달하고, 민감정보를 마스킹한다. 실제 대상 연결은 로컬 ID로 해결한다.
- 삭제·만료된 미리보기는 후보 갱신이나 프롬프트에서 되살리지 않는다. 원문 로그를 남기지 않는다.
- 중요한 알림 본문, 낮은 우선순위 기록, Jev의 단기 문맥 버퍼 보관은 설정 후보 보관과 별개의 정책이다. 애매한 분류는 바로 폐기하지 않는다. OS 원본 알림 취소는 이번 범위에 포함하지 않는다.

## 단계별 배치와 완료 기준

| 단계 | 추가 개발 범위 | 완료 판정 |
|---|---|---|
| Phase 0 후속 검증 | 방 구분·재수신·재부팅 식별 안정성과 누락 필드 관찰 | 확인/미확인/OEM 의존성을 기록하고 지원 범위 결정 |
| Phase 1 | 기존 Jev 분류 평가 유지, 지시 모호함과 모델 오류 분리 | 같은 데이터의 최초/보완 지시 비교, 중요한 알림 누락 측정 |
| Phase 2A | 목록·초안·공통 질문·재개 흐름을 합성 후보로 구현/검토 | 앱 종료 후 복원, 빈 후보, 새 후보 유입, 수정 중 이탈 검증 |
| Phase 2B | 최신 후보 저장·조회·만료, LLM 질문 구성 및 기능 안내 연결 | 실제 대상 카드 선택, 잘못된 ID 거부, 미지원 요구 안내 검증 |
| Phase 2C | OpenAI 정책 생성, 변경 비교·충돌 확인, 버전 적용·되돌리기 | 미완성 미적용, 원자적 교체, 오류 시 이전 기준 유지 검증 |
| Phase 3 | 활성 기준만 실시간 분류에 전달 | 일반 반복 분류의 LLM 호출 0회, Watch 조건부 요약 별도 측정, 대상 불명확 시 숨김 금지 검증 |

순서는 기존 Phase 게이트를 따른다. Phase 2A/B/C는 Phase 2 내부 작업 단위다. 실제 API 연결은 인증·키 보호·전송 정책과 함께 구현하며 비밀 키를 APK에 포함하지 않는다.

필수 검증 시나리오:

- 즉시 완료 가능한 지시, 여러 조건/예외가 있는 지시, 상충하는 지시, 명확한 부분 변경.
- 대화 후보 없음 → 이탈 → 새 알림 → 재진입 → 최신 후보 선택 → 적용.
- 미완성 여러 개를 목록에서 각각 재개하고 답변이 섞이지 않음.
- 이름 없는 방, 동일 이름의 다른 방, 요약 알림, 방 식별값 변경, 수집 권한 없음.
- 화면에 보인 후보 만료, 선택된 후보 삭제, 화면 이탈/프로세스 종료/재부팅.
- LLM/Jev 실패·타임아웃·잘못된 형식·없는 후보 생성·지원하지 않는 조건 제안.
- 기존 기준 수정 중 중단, 다른 버전 적용 후 오래된 초안 제출, 이전 버전 복원.
- 중요한 알림 누락 변화, 질문 수, 완료까지 왕복 수, 중도 이탈, 호출 수·입력량·latency·예상 비용을 함께 기록. 명확화가 정확도를 개선했다고 미리 단정하지 않음.

## 작업량 추정과 미결정 사항

현재 코드/검증 기록과 위 범위에 근거한 초기 추정이다. 외부 일정 자료나 실제 구현 속도 측정에 근거한 확정 견적은 아니다. Android 개발자 1명, 하루 집중 개발 6시간 기준의 작업일이며 병렬 작업을 가정하지 않는다.

| 작업 | 예상 작업일 |
|---|---:|
| UX 흐름·상태·질문/데이터 계약 확정 | 2~3 |
| 대화 메타데이터 저장·마이그레이션·최근 후보·만료 처리 | 3~5 |
| 기준 목록·초안 저장·공통 입력·재개 UI | 4~6 |
| OpenAI 질문 흐름·후보 조회·기능 안내·응답 검증 | 3~5 |
| Jev 연결·충돌 처리·버전 교체·복원 | 3~5 |
| Galaxy 흐름 검증·회귀·개인정보/비용 확인·수정 | 3~5 |
| 합계 | 18~29 |

1인 순차 진행으로 약 4~6주 분량의 기본 작업량, 식별 안정성·API 응답 처리 재작업을 감안한 계획 여유는 약 5~8주다. 기존 Phase 0/1 잔여 작업, 운영용 API 중계 서버/인증 신규 구축, 전체 앱 시각 디자인, 베타 장기 관찰, 후속 기능은 제외한다. 기존 Phase 2 단순 파이프라인을 대체하는 전체 추정이며 기존 견적에 중복 가산하지 않는다. API 사용료는 호출량 측정 후 별도 산정한다.

첫 작업은 위 대표 흐름을 합성 후보로 검토하는 것이다. 실제 데이터 식별 가능 범위와 화면 단계가 확인되면 다시 추정한다. 그때 후보 보관 한도, 미리보기 범위, 낮은 우선순위 알림 보관 정책, API 중계 배포 방식을 확정한다. 범용 규칙 편집기·임의 UI 생성·참여자 명단 추론·주기적 LLM 호출은 MVP에 포함하지 않는다.

## UI/UX 및 AI Watch 추가 범위 — 2026-09-23

[추가 개발 범위](UI_UX_AI_WATCH_SCOPE.md)에 따라 동일 기준 목록/공통 보완 흐름에 Watch 대상 대화·의미 변화 조건·본인 호칭·기본 관계 연결을 포함한다. 미완성 Watch는 활성화하지 않는다. Topic/Relationship은 별도 데이터 축이고 사용자 정의 category builder는 제외한다.

기존의 설정용 최신 후보 보관과 Watch의 지속 문맥은 다른 목적이다. 후보 미리보기200자 제안값을 Watch 문맥에 적용하지 않는다. 기존18~29작업일은 Phase 2 추정이며 Watch 실행·Timeline 전체 구현 견적이 아니다.

LLM의 반복 알림 분류 금지는 유지한다. 사용자 추가 지시에 따라 Jev가 알릴 시점으로 판단한 Watch 사건의 짧은 맥락 요약만 예외로 추가한다. 후보만 갱신될 때 자동으로 LLM을 호출하지 않는 기존 규칙과 구분한다.

## 정책 JSON 저장 전 검증

[Policy JSON Validation](POLICY_JSON_VALIDATION.md)을 설정 파이프라인의 필수 계약으로 포함한다. 결정론적 검사와 위험 기반 의미 검증을 분리하고, clarification_required 응답은 기존 공통 질문 UI로 연결한다. 검증 후에도 의미 있는 변경은 Diff 확인을 받고 저장하며 실패/이탈 시 기존 활성 버전을 유지한다.
