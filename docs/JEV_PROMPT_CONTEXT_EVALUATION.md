# Jev 프롬프트·시간순 문맥 재평가

2026-09-21. 사용자 요청으로 합성 데이터만 사용해 756회 API 호출을 완료했다. Android 앱에는 적용하지 않았다. 기대 정답·질문·임계값은 각 실험 호출 전에 고정했다. 이번 결과를 보고 재질문하거나 유리한 응답을 선택하지 않았다.

## 판단

프롬프트와 누적 문맥은 중요 알림 판단에 영향을 줬다. **문맥 및 정책 적용 기준을 명시한 B를 다음 개선의 출발점으로 삼을 만하지만, 모든 조건에서 중요 알림 누락이 가장 적은 것은 아니다.** 예시를 추가한 C가 더 좋다는 근거도 부족하다. 자동 숨김의 운영 검증은 아니다.

## 프롬프트 비교

- A: 기존 지시. 현재 알림과 최근 대화를 참조하라는 간단한 설명
- B: 시간순 해석·생략된 목적어 복원·최신 정정 우선·완료된 과거 사건 재알림 방지·본인/타인 구분과 yes/no 기준 명시
- C: B에 별도 합성 예시 4개 추가

세 조건 모두 동일한 Jev 1.13.0, 같은 입력/정답, 사건 Choice와 중요 여부 Noul 두 질문, 중요도 0.5 기준이다. 예전 5질문 실행과는 조건이 달라 이번 A를 대조군으로 사용한다.

|데이터|지시|중요도 정답|중요 알림 누락|불필요한 알림 판정|사건 분류 정답|
|---|---|---:|---:|---:|---:|
|기존 120건|A 기존|113/117 (96.6%)|3/79|1/38|117/120|
|기존 120건|B 기준 명시|115/117 (98.3%)|1/79|1/38|119/120|
|기존 120건|C 예시 추가|114/117 (97.4%)|2/79|1/38|119/120|
|신규 시간순 60단계|A 기존|55/60 (91.7%)|1/33|4/27|56/60|
|신규 시간순 60단계|B 기준 명시|57/60 (95.0%)|2/33|1/27|56/60|
|신규 시간순 60단계|C 예시 추가|56/60 (93.3%)|2/33|2/27|57/60|

기존 세트 중요도 정답이 null인 3건은 이진 채점에서 제외한다. 60단계는 12개 대화의 단계들이므로 독립적인 60개 대화로 해석하면 안 된다. 5단계 중요도를 모두 맞힌 대화는 A 8/12, B 9/12, C 9/12다.

B는 신규 세트에서 과잉 알림을 4→1건으로 줄였지만 누락을 1→2건으로 늘렸다. 중요 알림 누락을 더 위험하게 보는 프로젝트 원칙상 **전체 정답률만으로 B의 승리라고 결론내리지 않는다.**

## 문맥 누적 효과

12개 대화에서 각 메시지가 도착한 시점까지의 과거만 전달했다. 현재 메시지만 주는 조건은 같은 입력에서 과거를 제거했다. 실제 전체 맥락 정답으로 채점하므로 문맥 없는 조건의 실패는 정보 부족도 반영한다.

A에서 현재 메시지만 주면 중요도 정답 50/60, 누락 8/33이었다. 시간순 누적 시 정답 55/60, 누락 1/33으로 개선됐다. 다만 과잉 판정은 2→4건으로 늘어, 과거의 중요성을 이미 완료된 사건에 끌고 오는 문제가 있었다.

B 누적은 완료된 회비나 답변 처리 뒤의 과잉 판단을 줄였다. 반대로 예약 접수/발권 완료까지 “끝난 일”로 취급하는 부작용이 나타났다. **끝난 할 일과 새로 도착한 완료 통지는 분리해야 한다.**

### 10개·30개 누적 스트레스

6개 중요 사례에서 과거 요청과 현재 사이에 중립 잡담을 추가했다. 조건별 6건이며 모두 중요 알림이므로 이 실험만으로 과잉 판정을 평가할 수 없다.

|전체 메시지 수|A 누락|B 누락|C 누락|
|---|---:|---:|---:|
|10|1/6|0/6|0/6|
|30|1/6|0/6|0/6|

사건 분류는 모든 조건 6/6 일치했다. B/C는 이 사례들에서 중요도 점수가 모두 0.8 이상이었다. 작은 인공 스트레스 세트이며 실제 30개 메시지 대화의 일반 정확도를 뜻하지 않는다.

## 좋아진 부분과 남은 문제

- 기존 “내일까지 부탁해”의 미납 맥락과 시안 선택/고객 답변 요청을 B가 개선했다.
- B/C 모두 “식당 예약 접수 완료”와 “승차권 발권 완료”의 알림 중요도를 낮게 판단했다. 완료 처리 지시를 넓게 해석한 것으로 추정한다.
- “잘못된 미납 안내이니 보내지 마세요”를 신규 정책은 알리라고 했지만 B/C는 중요도를 0.43으로 판단했다.
- C는 기존 “좋아, 그렇게 확정하자”를 0.44로 판단했다. 예시를 추가한다고 항상 개선되지 않았다.
- 기존 납부 철회 사례의 라벨은 조용히 처리지만 A/B/C 모두 알려야 한다고 판단했다. 라벨/정책 경계의 이견은 유지하며 사후 정답 수정은 하지 않았다.

높은 점수 기준도 따로 봤다. 0.8 미만인 중요 알림 수는 기존 세트에서 A 18, B 25, C 21건으로 B가 오히려 늘었다. 신규 누적 세트에서는 A 13, B 6, C 4건으로 줄었다. 따라서 **0.5 정답률이 개선됐다고 기존 앱 알림 임계값 0.8에서 행동까지 개선됐다고 볼 수 없다.** 이번 실험은 실제 숨김/표시를 수행하지 않았다.

## 응답 품질·비용·검증

- HTTP 200: 756/756, 재시도 없음
- 검증 통과: 754/756. 두 실패는 문맥 없는 조건에서 Choice 선택값이 반환 확률의 최댓값과 불일치했다. GENERAL 0.34를 선택했지만 REPLY_REQUIRED 0.35, 또는 REPLY_REQUIRED 0.39를 선택했지만 UNKNOWN 0.40이었다. 원본 보존, 자동 수정/재호출하지 않음
- 주 비교의 JSON 구조는 모두 파싱 가능했다. 확률 합은 반올림을 고려해 사전 공통 허용오차 0.051 적용. 이전 엄격 검사의 0.001과 다르므로 통과율을 직접 비교하지 않음
- 요청 p50은 조건별 약 650~732ms. 실행 동시성/네트워크 영향이 있으므로 프롬프트별 속도 우위를 단정하지 않음
- 입력 1,248,432 / 출력 97,489 토큰. 추정 $0.052434 ([공식 입력 가격](https://docs.typesafe.ai/models), 입력 100만 토큰당 $0.042, 출력 무료, 실제 청구서 미확인)
- 시간순 prefix·미래 메시지 누출 방지·조건별 입력/정답 일치·반올림과 잘못된 확률 검증 자동 테스트 2개 통과
- 각 대화 첫 단계는 문맥 유무 두 조건의 입력이 동일하다. 12쌍씩 비교했을 때 이진 판정 변화는 없었지만 점수 차이는 A 최대 0.04, B/C 최대 0.01이었다. 0.5 근처의 작은 차이를 모두 프롬프트만의 효과로 단정하지 않음

## 다음 검증

B의 짧은 명시적 기준을 바탕으로 “완료 통지”, “요청 철회”, “약속 확정”을 구별하는 질문을 개선하고 새 대화 단위 검증셋에서 누락과 과잉을 함께 측정하는 것이 적절하다. 이번 자료를 계속 튜닝한 후 같은 자료 점수만 높이는 것은 피한다. 아직 실제 알림·긴 다중 화자 대화·반복 실행 안정성·Android 실시간 연동은 미검증이다.
