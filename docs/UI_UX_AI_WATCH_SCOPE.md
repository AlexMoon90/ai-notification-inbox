# UI/UX 및 AI Watch 개발 범위

2026-09-23 사용자 추가 지시 반영. [사용자 원문](requirements/UI_UX_AI_WATCH_USER_2026-09-23.md)을 보존한다. 이 문서는 개발 범위·검증 기준이며 구현 완료 기록이 아니다. 현재 Phase 0 미완료를 유지한다. 기존 단계 안에 추가 작업을 배치하며, 단계 실패를 건너뛰지 않는다.

## 확정한 제품 방향

Android Notification Center의 복제가 아닌, 사용자가 요청한 정보를 의미 단위로 읽고 이해하는 제품이다. Smart Inbox는 이벤트를 정리하고, AI Watch는 사용자가 선택한 대화에서 맥락 변화와 참여 시점을 감지한다. AI Watch를 핵심 유료 가치 검증 대상으로 MVP 개발 범위에 포함한다. 결제 시스템·요금제 확정은 이번 범위가 아니다.

## 화면과 정보 구조

- 기본 진입 화면은 최신순 Timeline이다. 수신/관찰 시각과 약속 등 사건 발생 시각을 분리한다. 예정된 약속 시각 때문에 오래된 알림이 최신 수신으로 오인되지 않게 한다.
- 큰 카드 대신 compact list row를 우선한다. 각 row는 이벤트 유형, 근거 있는 핵심 내용, 출처 앱, 상대 시각을 표시하고 필요한 경우 관계/맥락 태그를 추가한다.
- 상단 전환은 Timeline / Topic / Relationship. Source는 보조 필터 또는 메뉴이며 동등한 네 번째 기본 탭으로 만들지 않는다.
- Topic 초기 집합: 일정, 돈, 답변/요청, 업무, 개인, 배송/예약, AI 작업.
- Relationship 초기 집합: 업무, 가족, 친구/모임, 개인, 서비스, AI/도구. 알 수 없는 관계는 미지정으로 남기며 사용자가 지정/수정할 수 있다. 방 이름·본문만으로 가족/회사 관계를 확정하지 않는다.
- 세 View는 동일 이벤트의 다른 관점이다. 복제된 이벤트·서로 다른 정책 결과를 만들지 않는다. Source 필터는 모든 View에 일관되게 적용한다.
- 사용자 정의 카테고리 생성·이름 편집·구조 편집은 MVP 제외, v1.1 이후 후보. 기본 관계를 대상에 연결하는 기능은 카테고리 생성과 다르다.
- row 선택 → Event Detail의 요약 → 근거가 된 원본 알림/메시지 → 원래 앱 순서로 연결한다. Android 테스트 앱은 Timeline·원문 상세·원래 앱 연결을 구현했다. AI 이벤트 요약 및 자동 분류가 없는 수신 알림 화면이며 최종 이벤트 UI 완료로 세지 않는다. [구현·검증 범위](ANDROID_APP_EXPERIENCE.md).

Timeline에는 사용자 정책상 허용된 이벤트를 표시한다. 명시적으로 제외된 광고·일반 잡담·프로모션은 재노출하지 않고, 필요하면 별도 설정/히스토리로 둔다. 앱이 임의로 ‘긴급/매우 중요/낮음’을 붙이거나 우선순위별 대시보드로 시간순을 대체하지 않는다. ‘답변 필요’는 관찰된 사건 유형이며 임의 긴급도 등급이 아니다. ‘결제는 즉시 알려줘’처럼 사용자가 지정한 전달 방식은 적용한다.

판단 불확실과 확정 제외를 구분한다. 기존 보수적 원칙에 따른 ‘원본 확인 필요’는 별도 상태로 표시하고 확정 광고를 다시 끌어오는 용도로 쓰지 않는다. 500자 긴 카카오톡 원본 확인은 사용자가 승인한 확인 기준으로 유지한다. 명시적 전체 대화 제외와 원본 확인 기준이 충돌하면 설정 단계에서 우선순위를 정하고 자동 추정하지 않는다.

## Event 데이터 계약

하나의 category에 모두 넣지 않는다. 다음은 구현할 개념 필드이며 현재 Room 스키마에 존재한다는 뜻이 아니다.

|축/필드|역할|
|---|---|
|event_id / event_type|일정 확정, 납부 요청, 답변 필요, AI 작업 등 사건 식별|
|topic / relationship|내용 유형과 생활 관계를 별도 저장. 미지정 허용|
|source_app / source_profile / conversation_ref|앱과 프로필·대화 출처. AI 발신자 이름과 전달 앱은 별도|
|observed_at / event_time 후보|수신·관찰 시각과 사건 시각 분리|
|핵심 값 및 evidence_refs|시간·금액·장소·기한의 원문 후보와 근거 연결|
|policy_version / watch_ref|어떤 사용자 기준과 Watch로 만든 이벤트인지 추적|
|review_required / context_completeness|본문 잘림 가능성·누락·추가 확인 여부|
|판정 확률/요약 버전|내부 검증용. 제품 화면에 confidence/JSON을 노출하지 않음|

원문에 없는 값은 비워둔다. 서로 다른 앱의 같은 이벤트 유형도 같은 구조를 쓰며 source metadata로 구분한다. 확률은 검증 없이 신뢰도 보장으로 해석하지 않는다. AI 작업 사건은 [별도 검토](AI_WORK_RESULT_NOTIFICATIONS_REVIEW.md)의 관찰된 승인/답변/완료/실패와 원본 연결 원칙을 따른다.

## AI Watch 설정과 실행

사용자가 특정 대화를 선택하고 ‘약속이 정해지거나 내가 답해야 할 때’처럼 조건을 설정한다. ‘중요한 결정’의 의미, 본인 이름/호칭, 대상 대화가 부족하면 기존 공통 기준 확인 화면에서 보완한다. Watch 목록에서 대상·현재 조건·켜짐/꺼짐·설정 미완성·수집 제한 상태를 볼 수 있게 한다. 별도 전용 질문 엔진을 만들지 않는다.

```text
선택된 conversation의 실제 수신 알림
→ 로컬 Room에 관찰 메시지 누적
→ 제한된 최근 context를 Jev가 판정
→ 사용자 정책 + 알려줄 의미 있는 변화 + 앱의 중복/비용 검사
→ 필요할 때만 LLM 짧은 맥락 요약
→ 근거 검증 → 이벤트 갱신 및 사용자 알림
```

Jev 판정 대상: meaningful_change, decision_reached, user_directly_addressed, user_reply_required, conversation_waiting_for_user, user_action_required, user_interest_match, should_notify_user. 이들은 typed 확률 판단의 목표 항목이며 모든 필드를 한 번의 응답으로 확보했다고 가정하지 않는다. 원문의 0.9x 수치는 예시다. 임계값·개별 호출 수·정확도는 Phase 1 검증에서 결정한다.

LLM은 Jev가 알릴 후보를 판정한 시점에만 사용자가 이해할 짧은 맥락을 요약한다. LLM이 반복 분류나 실행 정책 생성 주체가 되지는 않는다. 이전의 ‘설정 시에만 LLM’ 원칙은 이 조건부 요약에 한해 사용자 요청으로 확장한다. 신규 메시지마다, 주기적으로, 후보 갱신만으로 LLM을 호출하지 않는다.

동일 사건의 반복 알림은 기존 이벤트를 갱신하고 중복 푸시/요약 호출을 억제한다. 하지만 새 질문·결정 변경·새 행동 요청은 묶음 처리로 놓치지 않는다. 사용자 정책과 실제 대상 검증을 거치며 Watch가 자의적인 중요도를 덧붙이지 않는다. 목표는 메시지20개를 읽는 부담을 맥락 알림1개로 줄이는 것이다. 원본 앱 알림20개를 자동 취소하는 권한/동작까지 추가한 것은 아니다.

요약 지연·실패·비용 한도 도달 시 확인이 필요한 사건 자체를 버리지 않는다. 짧은 유형/근거/원본 확인 안내로 대체한다. 동일 사건에 대한 중복 실행·재시도·프로세스 재시작도 측정한다.

## Conversation context와 보관

Room을 지속 저장 원본으로, 메모리를 최근 context 캐시로 사용한다. 프로세스 종료·재부팅 후 Watch 설정, 관찰 메시지, 마지막 처리 위치 및 알린 사건을 복원한다. 단순 메모리 버퍼만으로 구현하지 않는다.

- 활성 문맥의 초기 실험 범위는 최근10~30개 메시지 또는30~60분이며 토큰 상한을 함께 둔다. 이는 확정된 보관 기간이 아니다. 메시지 수·시간창 결합 방식과 만료 정책은 평가 후 확정한다.
- 중요 이벤트만으로 문맥을 만들면 일반 대화 속 근거를 잃는다. Watch가 켜진 대화의 허용된 관찰 메시지는 Timeline 표시 여부와 분리해 제한적으로 보존한다.
- 설정용 최근 후보(대화별 미리보기), Watch 최근 문맥, 이벤트 근거, 디버그 원문 기록은 서로 다른 보관 목적이다. 후보 미리보기200자 제안값을 Watch 문맥 본문에 적용하지 않는다.
- MessagingStyle 반복 이력과 같은 알림 갱신을 중복 메시지로 누적하지 않는다. 지연·순서 역전·같은 방의 다른 사건을 고려한다.
- 앱/프로필/검증된 대화 식별자를 사용한다. 방 이름·groupKey만으로 합치지 않는다. 식별이 없거나 바뀌면 맥락을 자동 병합하지 않고 연결 재확인을 요구한다.
- 원문은 가능한 한 로컬 저장하고 외부 Jev/LLM에는 필요한 최소 문맥과 마스킹만 전달한다. debug/release 모두 원문 로그 금지. 대화 의미에 필요한 가명은 요청 안에서 일관되게 유지한다.
- Watch 끄기·삭제·문맥 삭제는 별도 선택으로 명확히 한다. 삭제된 문맥을 캐시·재시도·복원에서 되살리지 않는다. 자동 만료의 실제 기본값은 실사용 연결 전에 확정한다. 7일/30일/즉시 삭제 사용자 보관 설정은 검토 후보이며 이번에 확정하지 않는다.

## 수집 가능 범위와 긴 메시지

Watch 활성화 전에 ‘원본 앱 알림과 메시지 미리보기가 필요하며, 알림으로 오지 않은 메시지는 볼 수 없다’고 안내한다. 대화 전체 기록·모든 참여자·내가 원래 앱에서 답했는지·다른 기기의 활동을 확보한 것으로 가정하지 않는다. 최근 관찰된 메시지가 없다고 연결 정상 또는 사용자의 무응답을 단정하지 않는다.

카카오톡은 이번 실기기 사례에서1369자 중 앞500자만 저장됐으며, 보편적인 길이 상한과 손실 발생 단계는 아직 확정되지 않았다. [검증 기록](KAKAO_LONG_MESSAGE_TEST.md). 현재 구현한500자 이상 원본 확인 표시를 유지한다. 이 기준을 다른 메신저에 무조건 일반화하지 않는다.

이전 문맥과 현재 부분 본문으로 의미를 판단할 수 있지만, 관찰되지 않은 끝부분·최종 결정·시간·금액을 만들어내지 않는다. 정보가 부족하면 ‘원본 확인 필요’로 남기며, 요약이 원문을 모두 읽은 것처럼 보이지 않게 한다. 긴 문서를 완벽하게 읽고 요약하는 기능은 범위 밖이다.

## 단계별 구현 및 완료 기준

|단계|추가 범위|완료 기준|
|---|---|---|
|Phase 0|메신저 수집·긴 본문·대화 ID·재시작 및 알림 설정 제한 검증|확인/미확인/OEM 의존성 기록. 기존 최소5앱 게이트 유지|
|Phase 1|Jev 단일 메시지와 누적 문맥 비교, Watch 의미 변화·답변 대기 판정 및 조건부 짧은 요약 합성 평가|중요 요청 누락·잘못된 결정 확정·환각·중복·언어별 결과·호출량/비용/지연을 분리 보고. 실패 해결 전 제품 연결 금지|
|Phase 2A~C|기존 지시 보완 흐름에 Smart Inbox/Watch 범위·실제 대화 선택·본인 호칭·관계 태그·활성 정책 연결|미완성 Watch 미작동, 잘못된 대화 ID 거부, 부분 수정과 이전 버전 유지|
|Phase 3A|기존 일반 알림 정책 분류|일반 알림의 설정용 LLM 호출0, 확정 제외/불확실 구분|
|Phase 3B|Watch Room/캐시·문맥 누적·Jev 변화 판정·중복 억제·조건부 LLM 요약|프로세스 종료 후 복원, 다른 대화 오병합 없음, 변화 없으면 요약 호출0, 실패 시 확인 경로 보존|
|Phase 4A|Timeline compact row·Topic/Relationship·Source 보조 필터·Event Detail|기본 최신순, 같은 이벤트 일관성, 확정 제외 재노출 없음, 임의 긴급도 표시 없음, 근거/원본 이동|
|Phase 4B|Watch 목록·수집 제한 안내·맥락 요약 알림·원본 확인|대화20개→필요한 순간 안내 시나리오, 새 행동 요청 누락 방지, 끄기/삭제/재개/중복 알림 검증|
|Phase 5|원문 후보 추출 및 이벤트 핵심 값 검증 강화|날짜/시각/금액/장소가 원문 근거로 연결. Phase 4에서도 검증 전 값을 추측해 표시하지 않음|
|Phase 6|Smart Inbox+Watch 비공개 베타|읽기 부담 감소·놓친 행동 요청·사용자 수정·반복 알림·원본 열기·유료 의향·비용을 측정|

A/B는 기존 Phase 안의 작업 단위이며 단계 순서를 바꾸지 않는다. Phase 0 디버그 화면은 데이터 수집 검증용이고 최종 Timeline 구현과 다르다.

## 필수 검증 시나리오

1. 논의→제안→확정, 확정 후 변경/취소. 단순 제안을 확정으로 만들지 않음.
2. 사용자 호명만 있음/직접 질문/타인에게 질문/사용자가 답해야 진행 구분.
3. 메시지20개와 같은 알림 갱신 반복에서 의미 변화만 통지. 별도 새 질문은 누락하지 않음.
4. 카카오톡 긴500자 미리보기의 마지막 미관찰 조건을 생성하지 않음. 문맥이 충분한 판단과 원본 확인 필요를 구분.

## 기존 범위와 일정 해석

[기준 설정 범위](POLICY_SETUP_SCOPE.md)의18~29작업일은 기존 Phase 2 추정이다. 이번 UI/Watch 전체 일정으로 재사용하지 않는다. 신규 작업 묶음은 이벤트 모델/마이그레이션, 세 View·상세, Watch 지속 문맥과 처리 상태, Jev 문맥 평가, 조건부 요약·중복·비용 제어, Galaxy/베타 검증이다. 수집 ID 안정성 및 문맥 평가 결과 후 별도 재추정한다. 본 변경에서 API 호출·앱 구현·기기 설치·성능 평가를 실행하지 않았다.
