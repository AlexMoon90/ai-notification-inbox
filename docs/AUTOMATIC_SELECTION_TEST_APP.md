# 개인 테스트 앱 — 자동 알림 선별

2026-09-23 사용자 요청으로 기준 검토 이후 실제 새 알림 선별을 연결한다. 기존 Phase 0 전체 통과나 상용 정확도 달성을 뜻하지 않는다.

## 사용 흐름

1. 기준 탭에서 기준을 만들고 질문에 답한다.
2. 정리된 기준을 읽고 ‘검토 완료로 저장’을 누른다.
3. ‘이 기준으로 선별 시작’을 누른 뒤 전송 범위 안내를 확인한다.
4. 이후 새 알림이 들어오면 Timeline에 ‘기준에 맞음 / 확인 필요 / 확인 중’을 표시한다. ‘기준 밖’은 별도 필터와 ‘전체’에서 확인할 수 있다.
5. 기준 탭에서 중지하거나 다른 검토 완료 기준으로 교체한다. 동시에 하나만 적용한다.

원래 앱의 시스템 알림을 삭제·차단하지 않는다. 별도 푸시를 추가하지 않고 Inbox 내 선별 결과를 시험한다. 적용 전 기록·수집기 재연결 당시 이미 떠 있던 알림은 자동 AI 전송하지 않는다. 앱을 닫았다 열어도 기준과 결과를 보존한다. 프로세스 종료 시 진행 중이던 판단은 재전송하지 않고 확인 필요로 복구한다. 기기의 알림 접근 및 인터넷 연결이 필요하며 앱 강제 종료/권한 해제 중 수집을 보장하지 않는다.

## AI 및 데이터 경로

- 기존 OpenAI Luna low 기준 정리/재질문 경로 유지.
- Jev `jev-1.13.0`가 지원 가능 여부와 특정 대화 식별 필요 여부를 typed Noul로 판단한다. 코드는 검토한 지시문 전체를 변경 없이 정책 JSON에 담는다. 조건을 짧은 태그로 축약하거나 생성된 문구로 바꾸지 않는다. 이는 자연어 의미 정책이며 모든 조건을 별도 실행 AST로 변환한 것은 아니다.
- 컴파일 지원 가능 판단은 ≥ 0.65, 대화 식별 필요 판단은 ≥ 0.5부터 실제 선택값을 요구한다. 실시간 제외 경계와 별개인 개인 테스트용 적용 게이트다.
- JSON에는 지시문, 실제 선택 대화 식별값, 모델, 판단 경계값, 컴파일 판단, 버전/시작 시각/초안 ID를 저장한다.
- 반복 선별은 Jev만 호출한다. 조건 충족과 근거 충분성을 한 요청에서 독립 판단한다. 본문 안의 명령은 데이터로 취급한다.
- 앱·제목·본문·발신자만 전송한다. MessagingStyle은 최신 timestamp의 메시지 하나를 사용한다. 전체 대화나 참여자 명단을 추측하지 않는다. 이메일/한국 휴대폰 번호는 동일 값끼리 일치하는 가명으로 치환하며 API 키 형태는 제거한다.
- debug APK에 기존 OpenAI/TypeSafe 테스트 키를 포함한다. release는 키와 설정 자산을 제외하고 원격 요청을 지원하지 않는다.
- 알림 원문은 Room, 정책/최근 최대 1,000개 결과는 기기 내부 AtomicFile에 저장한다. 최근 500개 알림 화면 범위는 유지한다.

## 보수적 처리

- 조건 충족 ≥ 0.8 및 근거 충분 ≥ 0.8: 기준에 맞음.
- 조건 충족 ≤ 0.05 및 근거 충분 ≥ 0.9: 기준 밖.
- 나머지는 확인 필요. 이 임계값은 개인 테스트용이며 대규모 보정 완료를 주장하지 않는다.
- 카카오톡 개별 500자 이상, 묶음 요약, 본문 없음, 입력 범위 초과, 오래 지연된 알림, 대화 식별 불명, API/응답 오류는 로컬에서 또는 판단 실패 후 확인 필요로 남긴다.
- 특정 대화는 package + Android 사용자 구분 + shortcutId의 해시로 결합한다. 이름/그룹 ID/알림 숫자 ID로 동일 대화를 단정하지 않는다. 기존 v1 기록은 v2 이관 시 식별값이 비어 있으므로 새 알림 후보가 필요하다. 불일치 식별값도 별도 확인 필요로 두며 다른 대화라고 단정해 숨기지 않는다.
- 하루 UTC 기준 최대 200건의 새 알림 판단 예약. 초과 및 큐 포화는 확인 필요. 자동 재시도 없음. 컴파일은 사용자의 시작 동작당 별도 1회.
- 동일 snapshot 재전달은 추가 판단하지 않는다. 중지/기준 교체 후 도착한 이전 요청 결과는 적용하지 않는다. 같은 문구라도 게시 시각이 다른 새 알림은 다른 snapshot이다.
- 호출 수, 입력/출력 토큰, 요청 바이트, latency, 추정 USD를 `jev-usage.jsonl`에 기록한다. 원문·키·예외 본문은 기록하지 않는다. 응답 사용량이 없는 실패는 비용 미상이며 0원으로 계산하지 않는다.

API/판단 설계 참고: [TypeSafe API](https://docs.typesafe.ai/api), [Noul](https://docs.typesafe.ai/primitives/noul), [불확실성 처리](https://docs.typesafe.ai/confidence), [guardrails 예제](https://docs.typesafe.ai/cookbooks/llm_guardrails). 가격 추정은 [공식 모델 가격](https://docs.typesafe.ai/models)의 입력 100만 토큰당 $0.042, 출력 무료 기준이다.

## 검증 기록

최종 단위 28개 통과, lint 오류 0개(기존 경고 1개), debug/release 빌드 통과. 두 키가 debug에 포함되고 release에는 포함되지 않음을 APK 바이트 검사로 확인했다. Galaxy S23/Android 16에 기존 데이터 유지 업데이트 설치를 완료했다. 화면 조작은 Galaxy 보안 잠금 해제 이후 별도 확인이 필요하다. API 진단에 사용한 합성 사례는 개발 중 입력과 경계값 조정에도 사용했으므로 별도 보류 평가셋의 정확도로 보고하지 않는다. 특정 원본 앱과 Android 알림 생성 단계에서 이미 줄어든 본문은 항상 탐지할 수 없다. 카카오톡 500자 안내도 확인 신호이며 모든 앱의 절단 판정이 아니다.

실제 개인 알림으로 광범위한 정확도 검증, 재부팅/장시간 절전/모든 앱의 대화 식별 안정성은 이번 합성 검사와 구분한다.


### 최종 실기기 결과

`AutomaticSelectionTest.liveListenerPolicyAndSelectionPersistWithoutPc` 통과. 실제 기기의 수집기 콜백에 합성 알림을 넣고 Room 저장 → Jev 정책 적용/분류 → 결과 영속 저장을 검증했다. OS가 실제 메신저에서 게시하는 경로를 다시 검증한 테스트와는 구분한다. 합성 대화 식별값으로 범위를 제한해 실제 개인 알림은 외부 AI에 보내지 않았다.

| 합성 사례 | 최종 결과 |
| --- | --- |
| 미납 전기요금 납부 요청 | 기준에 맞음 |
| 노트북 할인 광고 | 기준 밖 |
| 납부 완료, 추가 납부 없음 | 확인 필요 |
| 범위를 넘는 긴 본문 | 확인 필요, API 호출 없음 |

컴파일 1회 + 반복 판단 3회, 합계 4회. 각 알림 중복 재전달은 추가 호출하지 않았고 기존 기록 수는 유지됐다. 최종 검사 추정 비용 $0.000093114. 실패한 중간 검사와 PC 합성 진단을 포함하면 기기 12회 + PC 7회, 기록된 사용량 추정 합계 $0.000446502. 이 비용은 이번 Jev 작업만이며 기존 OpenAI 작업은 별도다.

중간 실패도 보존한다. 첫 컴파일은 선택 대화가 이미 결합됐다는 사실을 충분히 전달하지 않아 적용을 막았다. 상태/질문과 적용 게이트를 수정했다. 다음 검사에서는 명확한 납부 요청을 지나치게 높은 근거 경계값 때문에 보류해 표시와 제외의 경계를 분리했다. 장문 검사에서는 Android Notification.Builder가 테스트 입력을 먼저 줄여 추가 API 호출이 발생했으므로 extras에 의도한 합성 본문을 넣도록 fixture를 수정했다. 생산 입력의 모든 절단을 감지했다는 의미는 아니다.

최종 통합 검사는 음성 사례를 ‘기준 밖 또는 확인 필요’로 허용하면서 의미상 불일치 판단 ≤ 0.05도 검사한다. 확률의 미세 변동 때문에 보류되는 사례를 잘못된 중요 알림으로 승격하거나 억지로 제외하지 않는다. 납부 완료가 확인 필요로 남는 불필요 노출은 알려진 제한이다.

테스트 기준과 합성 기록은 정리했고 선별은 꺼 둔다. 사용자는 검토한 자신의 기준으로 시작한다. 화면 버튼 조작·실제 새 카카오톡 알림·장시간 백그라운드 검사는 별도 남아 있다. [기계 판독 결과](../evaluations/android-app-integration/AUTOMATIC_SELECTION_RESULT.json), [APK/단위 검사](../evaluations/android-app-integration/automatic-selection-apk-check.json).


### 적용 실패 오류 수정 — 2026-09-23

사용자가 기준 정리·재질문·저장을 마친 뒤 시작 버튼에서 실패한 사례를 조사했다. API 요청은 성공했고 selected/ref IDs도 빈 배열로 일치했다. 지원 가능성 판단 0.51/0.53이 기존 적용 기준 0.65에 못 미쳐 `unsupported`로 막혔지만, UI가 인터넷·지원 범위를 묶은 일반 오류만 보여준 것이 원인이었다.

컴파일 질문에 앱의 실행 범위를 명시했다. ‘받지 않는다/차단/숨김’은 이 Inbox의 표시 조건이며 Android 설정 변경 요청이 아니다. 허용·제외·명시적 예외의 조합을 모순으로 취급하지 않는다. 이미 수집 제외된 System UI/Android 두 출처는 예외 문구로 복원할 수 없으며 모든 출처는 실제 수신된 알림 범위다. 지시문·사용자의 답변·컴파일 문턱과 실시간 분류 문턱은 변경하지 않았다.

수정된 입력에서 신고된 저장 기준은 지원 가능성 0.88, 대화 식별 필요 0.10으로 통과했다. 과거 대화 조회 및 자동 답장은 차단, 미선택 특정 대화는 선택 필요, 선택 완료 대화는 통과하는 합성 대조 사례를 함께 확인했다. 임계값을 낮춰 실패를 우회하지 않았다. [진단 결과](../evaluations/android-app-integration/activation-fix-diagnostic.json).

오류는 기준 지원 여부, 대화 미선택/식별값 없음, 저장 기준 불일치, 네트워크, API 인증/한도/서버 오류, 기기 저장 실패를 분리한다. 외부 응답·예외 원문은 UI에 노출하지 않는다. 실패 시 기존 활성 기준은 유지한다. 최종 단위 30개·debug 빌드·lint 통과, release 키 제외 확인. 기존 합성 선별 실기기 검사도 통과했다(납부 요청 match, 나머지 3건 review; 의미상 비해당 판단은 별도 검사). Galaxy 실제 화면의 기준 탭 → 기존 저장 기준 → 선별 시작 → 확인 버튼 → 중지 버튼 표시 경로를 통과했다. 지시문과 답변은 변경하지 않았으며, 사용자가 시작하려던 기준을 활성화하고 저장했다. 최초 UI 검사는 확인창이 테스트 식별자를 상속하지 않아 멈췄고, 확인창 semantics를 보완한 후 통과했다.
