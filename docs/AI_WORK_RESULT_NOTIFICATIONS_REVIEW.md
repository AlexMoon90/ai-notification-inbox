# 여러 AI의 작업 결과 알림 수집·표시 검토

조사일: 2026-09-23. OpenClaw와 Claude/Claude Code를 중심으로 공식 문서와 현재 Android 코드를 검토했다. 실제 서비스 계정 연결·메시지 전송·새 기능 구현·실기기 검증은 하지 않았다. Phase 0 미완료 상태를 유지한다.

## 결론

서비스에서 Android로 실제 게시한 알림에 작업 상태나 행동 요청이 드러나면 현재 수집 경로를 바탕으로 분류할 수 있다. 권장 제품 방향은 ‘여러 AI의 결과와 내가 해야 할 일을 모아 보는 목록’이다. 알림에는 결과 파일 전체가 없을 수 있으므로 결과 요약·관찰된 상태·원본 이동을 제공한다. 알림이 오지 않은 작업까지 추적하려면 별도 직접 연동이 필요하다.

## 공식 문서에서 확인한 동작

|서비스/경로|확인 내용|우리 앱에 대한 의미|
|---|---|---|
|Claude Code → Slack|진행 업데이트 후 완료 시 사용자 멘션·요약·세션 보기/PR 생성 버튼을 제공한다. Team/Enterprise는 Claude Tag로 이전 중이고 Pro/Max는 기존 흐름을 사용한다.|Slack 알림의 완료 문구를 관찰할 수 있는 후보. Slack 화면의 버튼이 Android 알림에도 존재한다고 가정하면 안 된다. [문서](https://code.claude.com/docs/en/slack)|
|Claude Tag → Slack|스레드에서 업무를 수행하고, 장기 작업·일정 실행·사용자 판단이 필요한 내용을 전달하는 흐름을 소개한다.|단순 채팅 답변 외에 결과/사용자 확인 필요 사건을 대상으로 삼을 근거. 계정별 기능 제공·실제 알림 내용은 별도 확인한다. [제품 문서](https://claude.com/product/tag)|
|OpenClaw → 대화 채널|작업 종료 상태와 완료 전달 경로가 있고 실패/차단 진단, 선택적인 작업 링크를 제공한다. 전달 재시도가 중복 결과를 만들 수 있다.|완료/실패 분류와 중복 처리를 함께 설계한다. [작업 문서](https://docs.openclaw.ai/automation/tasks)|
|OpenClaw → Slack|원래 Slack UI에서 승인 버튼 등 풍부한 메시지를 지원한다.|우리 첫 범위는 요청을 보여주고 원래 Slack으로 이동하는 것. [문서](https://docs.openclaw.ai/channels/slack/rich-messages)|
|OpenClaw → WhatsApp|설정된 승인 전달 경로에서 실행/플러그인 요청을 전송하고 권한 있는 사용자의 반응으로 처리할 수 있다.|승인 요청 분류 대상. 채널 연결만으로 모든 승인이 자동 전달되는 것은 아니다. [문서](https://docs.openclaw.ai/channels/whatsapp#approval-prompts)|
|OpenClaw → 웹 알림|승인·질문·완료·실패 등을 위한 알림 설정이 있다. 공개되는 세부 내용은 제한될 수 있다.|본문이 일반적인 문구이면 상태만 표시하고 결과 내용을 만들어내지 않는다. [문서](https://docs.openclaw.ai/web/notifications)|
|Claude Code hooks|알림 이벤트의 종류·세션 ID 등을 전달할 수 있고 Stop/StopFailure 등도 제공한다. Stop은 응답 종료이며 항상 전체 작업 성공을 의미하지 않는다.|향후 직접 연동 후보. PC의 hook이 저절로 Android 알림이 되는 것은 아니며 전송 경로를 별도로 구성해야 한다. [문서](https://code.claude.com/docs/en/hooks)|

Claude를 WhatsApp에서 사용하는 경로는 사용자가 구성한 중계/봇일 수 있다. 위 조사를 근거로 Claude의 공식 WhatsApp 직접 연동이 있다고 단정하지 않는다. OpenClaw가 Claude를 내부 모델로 쓰더라도 알림에 드러나지 않으면 모델명을 추측하지 않는다.

## 가장 중요한 수집 한계

Android NotificationListenerService는 게시된 알림과 그 변경/제거를 관찰한다. 외부 서비스의 전체 작업 DB를 조회하는 권한이 아니다. [Android 문서](https://developer.android.com/reference/android/service/notification/NotificationListenerService)

Slack은 모바일 알림 시점과 대상에 별도 설정이 있다. PC 사용 여부, 멘션·스레드 설정 등 때문에 서비스에 메시지가 있어도 휴대폰 알림이 없을 수 있다. ‘알림을 못 받음’과 ‘Jev가 잘못 분류함’을 분리해서 측정해야 한다. [Slack 문서](https://slack.com/help/articles/360025446073-Guide-to-Slack-notifications)

서비스의 Slack 카드 전체, 버튼, 첨부 파일과 Android 알림 데이터는 서로 다르다. 노출된 본문·발신자·대화 정보만으로 가능한 범위를 결정한다. PC에만 표시된 알림을 현재 Android 앱이 직접 수집할 수는 없다. 업무 프로필 정책 등으로 리스너 접근이 제한될 수도 있다.

## 현재 코드와의 차이

현재 `NotificationNormalizer.kt`는 앱 패키지, 제목, 본문/확장 본문, 대화 제목, MessagingStyle의 발신자·본문·시각·MIME 종류를 읽는다. `NotificationData.kt`는 알림 키·스냅샷·그룹·채널 정보를 저장한다. contentIntent는 원본 열기 경로에서 사용한다.

아직 없는 것: AI 작업 사건 분류, 검증된 봇 신원 연결, 안정적인 외부 작업 ID, 작업 상태 목록, 승인 해결 여부 추적, 결과 파일 수집, 외부 서비스 승인 실행. 현재 알림 DB에 conversation shortcut ID를 영구 저장하는 구현도 없다. 알림 groupKey/channelId를 작업/대화 ID로 쓰면 안 된다.

따라서 ‘Slack/WhatsApp이 설치돼 있으니 해당 AI 작업을 전부 이미 받는다’고 말할 수 없다. Galaxy에서 서비스별 실제 알림 payload와 원본 이동을 확인해야 한다. 기존 시스템 패키지 제외는 유지한다. 일반 앱/브라우저가 게시하는 AI 알림을 모두 시스템 알림으로 제외하지 않는다.

## 제안하는 공통 분류와 UI

모든 AI를 개별 화면으로 만들기보다 기존 Inbox에 ‘AI 작업’ 보기와 상태 필터를 추가하는 방향을 제안한다. 우선순위는 사용자 기준에 따르되 초기 제안은 다음과 같다.

|사용자 표시|관찰해야 할 근거|표시/처리 제안|
|승인 필요|내 실행 허가를 명시적으로 요청|상단 확인 필요, 원본에서 검토|
|답변 필요|내 선택·추가 정보·결정을 요청|상단 확인 필요, 원본에서 답변|
|실패·중단|실패, 권한 부족, 사용자 조치가 필요한 중단을 명시|실패 이유가 보이면 짧게 표시|
|완료·결과 도착|작업 완료 또는 결과가 준비됐다고 명시|결과 요약/제목과 원본 열기|
|진행 중|시작·진행률·계속 처리 중이라는 정보|기본적으로 조용히 기록하는 선택 제공|
|내용 확인 필요|본문 없음·잘림·상태 불명확|완료/실패를 추정하지 않고 원본 확인|

‘완료’와 ‘내 검토 필요’는 동시에 성립할 수 있다. 내부적으로 사건 종류와 사용자 행동 필요 여부를 분리한다. ‘답변 완료’, ‘하위 작업 완료’, ‘전체 작업 완료’도 근거가 있는 범위만 표시한다. 성공했다는 알림은 결과 품질이 검증됐다는 뜻이 아니다.

아래는 실제 알림이 아닌 표시 예시다.

> 승인 필요 · OpenClaw로 지정한 봇 · WhatsApp
>
> 웹사이트 배포를 진행하기 전에 허가를 요청했습니다.
>
> 3분 전 받은 요청 · 현재 해결 여부는 원본에서 확인
>
> [원본에서 확인]

> 결과 도착 · Claude · Slack
>
> 로그인 오류 수정 작업이 완료됐다는 알림입니다. 변경 요약과 PR은 원본에서 확인하세요.
>
> [Slack에서 보기]

AI 이름은 명시된 발신자 또는 사용자 지정 출처에 근거해 표시한다. 확인되지 않은 경우 ‘Slack에서 받은 작업 알림’처럼 표시한다. 사용자가 지정한 봇 이름은 검증된 서비스 신원과 구분한다. 작업명·파일명·링크가 없으면 임의로 생성하지 않는다.

## 실행과 승인 범위

첫 버전은 승인 요청을 찾아 보여주고 원래 앱/인증된 화면으로 이동한다. 우리 앱이 자연어만 보고 승인 요청을 실행하거나 👍 반응을 대신 보내지 않는다. 원본 서비스가 가진 승인 권한·만료·취소·해결 상태를 그대로 사용한다. 직접 승인 버튼을 만들려면 승인 ID, 최신 상태, 권한 확인, 중복 실행 방지를 갖춘 별도 연동 설계가 필요하다.

## 지시 정리 및 분류에 반영할 규칙

사용자 지시 예: ‘내가 지정한 AI 봇들의 승인 요청과 실패는 바로 알려줘. 완료 결과는 모아주고 진행 상황은 조용히 해줘.’

- LLM은 어떤 봇/방인지 부족한 부분을 질문하고 관찰된 후보 중 사용자가 선택하도록 한다. 이름에 Claude가 들어갔다는 이유만으로 본인 AI 작업으로 확정하지 않는다.
- 서비스/에이전트 이름과 알림 전달 앱을 별도 보관한다. Slack 전체를 특정 AI의 알림으로 분류하지 않는다.
- Jev는 반복 알림의 사건 의미 및 사용자 기준 해당 여부를 판단한다. 알림마다 설정용 OpenAI를 호출하지 않는다.
- 코드가 출처·원문 근거·사용자 설정·표시/원본 이동을 관리한다. 새 실행 정책 형식과 연결은 해당 Phase에서 검증한다.
- 불확실한 승인/답변 요청을 조용히 버리지 않고 확인할 수 있게 남긴다. 일반적인 ‘새 메시지’만 보이면 정체와 사건을 단정하지 않는다.

## 상태 갱신·중복 처리

알림 한 건은 ‘그 시점에 관찰된 사건’이다. 현재 서버 상태로 표시하지 않는다. 알림을 지웠다고 승인 완료로 바꾸지 않는다. 승인 만료·취소·다른 기기에서 처리됨은 해당 근거를 수신한 경우에만 갱신한다.

같은 알림 키의 갱신은 원문 이력으로 유지할 수 있다. 서로 다른 메시지/채널의 동일 작업은 신뢰할 수 있는 작업 ID·출처가 있어야 병합한다. 같은 방·비슷한 제목만으로 다른 작업을 합치지 않는다. 작업 ID가 없으면 개별 사건을 유지한다. 나중에 늦게 도착한 과거 알림이 최신 상태를 덮지 않도록 이벤트 시각/버전이 필요하다.

## 검증 순서 제안 — 아직 실행하지 않음

1. Galaxy 수집 확인: Claude/Slack, OpenClaw/Slack, OpenClaw/WhatsApp 각각 완료·승인 또는 질문·실패를 실제 수신해 앱 화면과 리스너 데이터를 비교한다. 계정/설치 버전에서 불가능한 종류는 불가능 또는 미확인으로 기록한다. PC 활성/휴대폰 알림 설정, 미리보기 제한도 비교한다. 테스트 목적으로 실제 위험한 작업을 실행할 필요는 없다.
2. 합성 판별: 사건6종 × 한국어/영어2 × 전달 출처4종 = 48개를 먼저 고정한다. 출처4종은 Claude/Slack, OpenClaw/Slack, OpenClaw/WhatsApp, 일반 AI 앱 가상 알림이다. 가상 출처는 실제 연동 지원 증거가 아니다.
3. 반례16개: 사람이 AI를 언급한 대화, 타인에게 보낸 승인 요청, ‘아직 완료 안 됨’, ‘완료되면 알림’, 하위 작업만 완료, 결과 생성 후 사용자 검토 필요, 과거 요청 인용, 해결/취소/만료, 같은 작업의 중복, 같은 방의 다른 작업, 순서 역전, 본문 잘림, 일반 새 메시지, 알림 속 지시 삽입 등을 포함한다.
4. 지표: 승인/답변 요청 누락, 잘못된 완료, 불필요한 긴급 알림, 출처 오인, 잘못된 병합, 원본 이동 성공을 별도로 본다. 고정 표본에서 핵심 행동 요청 누락이나 잘못된 완료가 남으면 제품 연결을 보류한다. 표본 통과와 전체 신뢰성을 구분한다.

권장 순서는 문서로 확인된 대화 채널의 Android 수신 가능성 확인 → 합성 Jev 평가 → 해당 Phase에서 카드 표시 구현이다. hooks/webhook 직접 연동은 Android 알림만으로 부족한 부분이 실제 확인된 후 확장 후보로 둔다.
